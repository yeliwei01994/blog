## 7/20-7/26 工作与学习记录

## 一、项目工作

### 1. 修复 Chatbot 下载按钮导致的 Hydration Error

本周首先修复了 Chatbot 中下载按钮的前后端首帧状态不一致问题。

问题的根源是：服务端渲染页面时，下载按钮的 `disabled` 状态与客户端 JavaScript 接管页面后的初始状态不同。Next.js 在浏览器中进行 hydration 时，会要求服务端生成的 HTML 与客户端第一次渲染的结果保持一致；一旦两边的属性不同，就会出现 hydration error。

```text
服务端首帧 HTML
下载按钮：disabled = true
        ↓
客户端首次渲染
下载按钮：disabled = false
        ↓
Next.js 发现结构或属性不一致
        ↓
Hydration error
        ↓
后续聊天交互无法正常继续
```

这个问题表面上出现在下载按钮上，但影响的是整段页面交互。因为 hydration 失败后，React 无法可靠地接管这部分页面，后续聊天消息、按钮点击等交互都会受到影响。

修复过程中重点是让服务端和客户端在第一次渲染时使用同一份确定的初始状态，等客户端完成挂载并拿到真实状态后，再更新按钮是否可用。通过这次问题，我更清楚地理解了 Next.js 服务端渲染和客户端 hydration 的关系：服务端负责先输出页面，客户端负责接管交互，但两边第一眼看到的页面必须一致。

### 2. 在生成前增加网站行业识别

本周还优化了网站生成前的需求处理流程。系统不再直接把用户的一句话交给生成模型，而是会先结合用户描述判断目标网站大致属于什么行业或场景，例如餐饮、咖啡店、电商、个人作品集、企业官网等。

```text
用户需求
        ↓
识别网站类型 / 行业场景
        ↓
补充对应的页面结构、内容重点和视觉方向
        ↓
生成网站代码
```

增加这一步的意义是让后续生成更有针对性。不同类型的网站关注点不同：

- 餐饮或咖啡店网站更需要菜单、门店信息、预约或联系入口；
- 电商网站更关注商品展示、分类、价格和购买路径；
- 企业官网更关注品牌介绍、服务内容、案例和联系方式；
- 个人作品集更关注个人介绍、项目作品和技能展示。

先完成行业识别后，Agent 可以带着更明确的上下文生成页面，而不是只依据通用模板拼出一个结构相似的网站。这也让我理解到，AI 生成网站并不只是“让模型写代码”，前面的需求理解和上下文整理同样决定了最终结果是否贴合用户真实需求。

### 3. Agent 工作流增加截图检查

之前 Agent 的主要闭环是：生成代码、构建项目、构建成功后部署。本周在构建验证之后增加了截图检查，使 Agent 不只判断“能不能编译”，还会继续检查“页面实际显示出来是否合理”。

```text
用户提出需求
        ↓
分析需求并识别网站场景
        ↓
生成或修改项目代码
        ↓
执行构建
        ↓
构建成功
        ↓
启动页面并生成截图
        ↓
检查页面视觉结果
        ↓
通过后部署
```

单纯的构建成功只能说明代码没有明显的语法、类型或打包错误，但不能说明页面视觉效果一定正确。例如页面可能出现布局错位、文字被遮挡、图片没有显示、按钮位置异常，或者生成内容和用户需求不匹配。这些问题在 `npm run build` 成功时仍然可能存在。

截图检查把验证从“代码层面”推进到了“页面结果层面”。如果发现页面存在明显问题，Agent 可以把截图和检查结果作为下一轮修复依据，再回到生成、构建和验证流程中。

```text
代码正确
不等于
页面正确

构建检查
  + 截图检查
  = 更完整的发布前验证
```

这次优化让我更能理解 Agent 的完整含义：它不是一次性输出答案，而是能够观察结果、发现问题、继续调整的执行闭环。

### 4. 新增图片生成 API 入口

本周新增了图片生成 API 入口，使网站生成流程可以调用图像生成能力，为页面提供更贴合主题的视觉素材。

在没有图片生成能力时，网站通常只能使用占位图、外部图片地址或简单的纯色布局；新增统一 API 入口后，系统可以把页面主题、行业场景和视觉需求传递给图片生成服务，再将生成结果用于网站页面。

```text
用户需求
        ↓
识别行业和页面主题
        ↓
构造图片生成提示词
        ↓
调用图片生成 API
        ↓
获得图片资源
        ↓
写入或引用到生成的网站中
```

把图片生成能力设计成 API 入口，而不是直接耦合到页面代码中，有利于后续替换不同的图片模型或服务，也能让 Agent 在需要视觉素材时通过统一方式调用。对于 AI 生成网站来说，文字、布局和图片共同决定最终体验；图片能力接入后，生成的网站会更接近完整的可展示页面。

### 5. 视频模型调研

本周对 Kling、Seedance 以及国内数字人产品进行了初步调研，重点不只是比较“哪家画面更好”，而是区分它们属于视频模型还是完整数字人平台，并关注后续 API 接入时的成本和产品边界。

首先，Kling Avatar 2.0、Seedance 2.0、腾讯云智能数智人、阿里云灵眸和火山引擎数字人并不是同一类产品：

| 产品 | 产品定位 | 更接近的使用场景 |
|---|---|---|
| Kling Avatar 2.0 | 异步数字人视频生成 | 人物图片、音频和表演提示生成口播或营销视频 |
| Seedance 2.0 | 通用多模态视频生成模型 | 人物、商品、场景和音频素材共同生成创意视频 |
| 腾讯云智能数智人 | 企业级数字人平台 | 形象、播报、实时互动、云/端渲染和并发管理 |
| 阿里云灵眸 | 数字人 PaaS/SaaS 平台 | 视频合成、实时会话、数字人资产和渲染接入 |
| 火山引擎数字人 | 多组数字人与视觉生成能力 | 克隆形象、单图音频驱动、改口型和视频驱动 |

其中，Seedance 并不是专门的数字人平台。它可以生成人物说话、动作和口型效果，但更偏向通用视频创作；如果后续要做固定形象管理、长时口播或实时互动，还需要配合 TTS、人物资产、任务管理和内容审核等能力。Kling Avatar 2.0 的输入和产品示例则更集中于“固定人物说话和表演”，但网页端能力是否以同等参数开放为开发者 API，仍需要在接入前确认。

价格方面，各家的计费单位并不统一，不能简单按每秒价格直接排序：

| 产品/能力 | 当前调研到的计费口径 |
|---|---|
| Kling Avatar 2.0 | Studio 侧 Standard 为 4 Credits/秒，Professional 为 8 Credits/秒；与开发者 API 的对应关系需确认 |
| Seedance 2.0 Mini | 0.023 元/千 Tokens |
| Seedance 2.0 Fast | 0.037 元/千 Tokens |
| Seedance 2.0 标准版 | 0.046 元/千 Tokens |
| 腾讯云 2D 播报视频 | 1800 美元/10 小时，形象、并发等项目单独计费 |
| 阿里云数字人视频合成 | 9.9 元/分钟，实时服务与形象定制另行计费 |

Seedance 按 Token 计费，实际消耗会受时长、分辨率、输入图片/视频/音频数量影响；腾讯云和阿里云则把形象、视频生成、实时互动和渲染资源拆分计费。因此后续实际选型不应只看单次调用价格，而要统一测试同一条任务的可用率：

```text
同一人物素材
        + 同一段口播文案或音频
        + 同样的视频时长与分辨率
        ↓
比较生成质量、等待时间、失败率和重试次数
        ↓
单条可用视频成本
= 总消耗 ÷ 最终可用视频数量
```

从能力边界来看，预录口播视频可以重点测试 Kling Avatar、阿里云视频合成、火山单图音频驱动，以及 Seedance 的人物视频效果；实时数字人场景则需要重点关注腾讯云和阿里云的会话、并发与渲染能力，不能直接用 Kling 或 Seedance 的异步视频生成替代。




## 二、Rust 学习进度

本周继续学习《The Rust Programming Language》的第 15 章和第 16 章。

### 第 15 章：智能指针

学习了 `Box<T>`、`Rc<T>`、`RefCell<T>` 等智能指针的基本概念，以及它们与普通引用的区别。

```rust
fn main() {
    let number = Box::new(5);

    println!("{number}");
}
```

`Box<T>` 可以把数据放到堆上，同时由 Box 拥有并负责释放这份数据。它常用于递归类型、较大的数据，或者需要在编译期无法确定具体大小的场景。

例如递归链表可以使用 `Box<List>`：

```rust
enum List {
    Cons(i32, Box<List>),
    Nil,
}
```

通过这一章，我开始理解智能指针不仅是“指向数据的地址”，还会附带所有权、引用计数或运行时借用检查等额外能力。

### 第 16 章：无畏并发

学习了线程、消息传递、共享状态并发，以及 `Mutex<T>` 和 `Arc<T>` 的基本使用。

线程可以让多个任务并行执行：

```rust
use std::thread;

fn main() {
    let handle = thread::spawn(|| {
        println!("running in a new thread");
    });

    handle.join().unwrap();
}
```

多个线程之间也可以通过 channel 传递消息：

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    thread::spawn(move || {
        tx.send("hello from thread").unwrap();
    });

    println!("{}", rx.recv().unwrap());
}
```

这一章让我认识到，Rust 的并发设计和所有权规则是连在一起的。编译器会帮助检查多个线程是否安全地访问同一份数据，尽量把数据竞争等问题提前暴露在编译阶段。
