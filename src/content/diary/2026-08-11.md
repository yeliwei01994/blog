### 项目结构的思路与学习

今天我重新梳理了官网项目的目录结构。此前我对“项目结构”的理解更多停留在文件分类：页面放页面目录、组件放组件目录，能实现功能就继续往下写。这种做法没有真正回答“这段代码为什么在这里”“它未来由谁维护”“它会影响哪些模块”。



### 1. 代码应按业务归属和变化范围组织

首先，首页、新闻、产品、解决方案等是不同业务模块。一个只服务新闻的卡片、数据或页面，应该和新闻业务放在一起；不能因为它“看起来像一个通用组件”，就过早放进全局 `components`。

只有当代码已经被多个业务真实使用，而且对外接口稳定时，才值得抽取为共享组件、通用 hook 或工具。这样可以避免共享目录逐渐变成什么都往里塞的“杂物间”。

### 2. 需要关注依赖方向，而不仅是文件位置

应用层负责组装路由、布局和业务模块；业务模块可以使用共享组件、工具和配置；但共享层不应该反过来依赖某一个具体业务。

如果共享组件需要 import 新闻、产品等具体业务的数据或组件，就说明边界可能没有划清楚。不能只看“能不能跑”，还要看依赖方向是否合理。

### 3. 工程质量需要靠校验机制

项目已有 lint、类型检查、环境配置校验、路由校验、目录结构校验和生产构建等机制。它们的意义不是增加流程，而是把容易遗漏的约定变成可以重复执行的检查。

例如新增路由时，不能只修改页面；还需要同步维护路径定义、路由注册和对应校验。新增图片时，也需要遵守资源目录和环境路径规则。

### 4. 目录模板不能机械套用

我也认识到 `features`、`components`、`hooks` 这套结构更适合多业务前端项目；后端、移动端、CLI、数据或 AI 项目应先遵守各自语言和框架的约定。

我需要学习的不是背一套目录，而是根据项目类型判断：代码的职责是什么、谁使用它、它会和谁一起变化、怎样验证这个设计是合理的。

## 我需要养成的工作习惯

后续每次开发前，我会先完成以下判断，再开始写代码：

1. 这次需求属于哪个业务模块？
2. 本次会修改哪些文件，为什么是这些文件？
3. 是否新增路由、静态资源、配置或对外接口？
4. 这段代码是业务专属，还是已经存在真实的跨业务复用？
5. 改动完成后，应该用什么命令或流程验证？


## 后续行动

将之前的项目chat bot 按照思路进行一下结构的优化。


### 开始时的状态

今天把之前的 chatbot-demo 作为一次实际练习进行了整理。项目最初能运行，但仓库根目录同时放着 Rust 后端源码、Next.js 前端、React/Vite 站点模板、Caddy 配置、Docker 文件、本地脚本、运行数据和质量文件。功能本身没有问题，但第一次打开仓库时很难判断每个目录是“可运行的应用”“平台配置”还是“本地生成的数据”。

当时前端在 `web/`，Rust 源码直接在根目录 `src/`，站点模板在 `templates/`，部署文件在 `deploy/`，脚本在 `scripts/`。这会带来两个问题：一是目录名称只能说明技术或历史来源，不能说明职责；二是后续移动文件时，Docker、脚本、编译期资源引用和视觉检查路径容易漏改。

优化前的目录大致如下：

```text
chatbot-demo/
├─ src/                         # Rust API 源码直接放在根目录
├─ web/                         # Next.js 工作台前端
├─ templates/react-vite/        # 用于生成网站的 React/Vite 模板
├─ deploy/                      # Caddy 配置
├─ scripts/                     # 启动、验证、质量检查脚本
├─ tools/caddy/                 # 本地 Caddy 二进制文件
├─ data/                        # SQLite 等本地数据
├─ uploads/                     # 项目上传与生成文件
├─ Dockerfile
├─ docker-compose.yml
├─ Cargo.toml
├─ Cargo.lock
└─ ROADMAP.md
```

可以看到，应用代码、部署配置、工具、运行数据和仓库级文件都处于同一层级。虽然每个目录单独看都能理解，但整体上缺少一条明确的组织主线。

### 优化思路

这次没有单纯按“文件类型”重新归类，而是先区分每部分在整个产品里的角色：

1. 可独立启动的程序放进 `apps/`；
2. 被应用复用、用于生成网站的工程模板放进 `packages/`；
3. Docker、Caddy、启动脚本等运行平台能力统一放进 `platform/`；
4. SQLite、上传内容、构建缓存等本地运行数据统一放进 `runtime/`，并通过 `.gitignore` 排除；
5. 路线图放进 `docs/`，质量场景规则保留在 `quality/`，生成报告不提交。

整理时的关键不是移动目录本身，而是同步检查所有路径依赖：Rust 的 `include_str!`、模板的相对路径、Docker Compose 的构建上下文、PowerShell 脚本、Caddy 配置，以及视觉检查脚本的位置。实际调试中也发现，视觉检查仍指向旧的 `web/scripts/visual-check.mjs`，导致构建成功后被错误判定为检查失败。修正为新路径后，真实生成项目的构建和视觉检查都通过了。

### 优化后的项目结构

```text
chatbot-demo/
├─ apps/
│  ├─ forge-api/                 # Rust + Axum API、生成编排、构建与视觉检查
│  └─ forge-workbench/           # Next.js 工作台前端
├─ packages/ **
│  └─ site-template/react-vite/  # 受控生成网站的 React/Vite 模板
├─ platform/
│  ├─ docker/                    # Dockerfile 与 Compose
│  ├─ gateway/config/            # Caddy 路由配置
│  └─ scripts/                   # 启动、验证和质量检查脚本
├─ runtime/                      # 本地数据库、上传文件和运行数据（不提交）
├─ quality/
│  ├─ scenarios.json             # 可提交的质量规则
│  └─ reports/                   # 本地测试报告（不提交）
├─ docs/                         # 项目文档与路线图
├─ skills/                       # 本地 UI/UX 辅助能力
└─ README.md                     # 架构、目录与启动说明
```

整理后，看到目录名称就能知道它服务于什么：要启动产品看 `apps/`，要改基础设施看 `platform/`，要调整生成模板看 `packages/`，本地运行留下的数据则只在 `runtime/`。根目录也只保留仓库级说明和忽略规则，减少了“所有东西都堆在顶层”的感觉。

### 后续维护原则

项目结构优化不是一次性搬家，而是建立边界。后续新增功能时，要先判断它属于应用、可复用模板、平台能力还是本地运行数据；新增路径后，要把相关脚本、容器配置和测试一起更新。每次目录调整完成后，也需要像功能开发一样执行构建、测试和真实运行验证，避免“结构看起来更整齐，但运行链路已经断掉”。
