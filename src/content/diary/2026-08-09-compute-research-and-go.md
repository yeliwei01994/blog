## 8/3-8/9 工作与学习记录

## 一、项目工作

### 1. 算力中心调研平台创建

本周开始创建算力中心调研平台。平台的目标是对算力中心相关信息进行集中整理和展示，后续可用于沉淀调研资料、对比不同算力中心的基础信息，并为进一步分析提供统一的数据入口。

在开始阶段，先围绕页面结构和信息展示方式进行了梳理，例如调研对象的基本信息、产品或服务能力、所在区域、资源情况和相关说明等。通过先把信息结构理清，再逐步补充页面内容，可以避免一开始只关注视觉效果而忽略后续数据整理和扩展的需求。

### 2. Supabase 数据库学习与使用

本周学习了 Supabase 的数据库使用方式，并开始思考如何把平台中的调研信息从静态内容转为可维护的数据。

Supabase 以 PostgreSQL 为基础，除了提供数据库外，也把表管理、SQL 操作、权限控制、认证、存储和 API 能力整合在一个平台中。对于前端项目来说，开发者不需要从零搭建一套数据库服务和基础接口，就可以先创建数据表、配置字段，并通过客户端或 API 读取和写入数据。

在学习过程中，重点理解了以下几个概念：

- **表（table）**：用于保存同一类数据，例如算力中心、调研记录或标签；
- **字段（column）**：用于描述每条数据的属性，例如名称、区域、介绍、创建时间；
- **行（row）**：一条具体的数据记录；
- **SQL**：用于创建表、查询、插入、更新和删除数据；
- **PostgreSQL**：Supabase 底层使用的关系型数据库；
- **Row Level Security，RLS**：按数据行控制访问权限，决定不同用户可以读取或修改哪些数据。

例如，算力中心信息可以抽象成一张表：

```sql
create table compute_centers (
  id bigint generated always as identity primary key,
  name text not null,
  region text,
  description text,
  created_at timestamptz default now()
);
```

前端后续就不必把每一条调研资料硬编码在页面中，而是可以从数据库查询数据：

```typescript
const { data, error } = await supabase
  .from('compute_centers')
  .select('*');
```

这样做的意义在于，后续新增或更新调研对象时，可以优先更新数据，而不是每次都修改页面代码。页面负责展示，数据库负责保存和管理数据，职责会更清晰。

### 3. 从静态 HTML 转向 Next.js 16 + React 19 + TypeScript

算力中心调研平台最开始是以静态 HTML 页面为基础进行搭建的。当时认为需求比较简单，先快速完成页面展示即可。但随着需要考虑数据维护、组件复用、页面扩展、数据库连接和后续功能迭代，单纯使用静态 HTML 的方式开始不够合适。

因此，后续将项目调整为工程化的 Next.js 16 + React 19 + TypeScript 技术栈：

```text
Next.js 16
  └── 路由、页面组织、服务端能力和项目结构

React 19
  └── 组件化组织页面和交互状态

TypeScript
  └── 为数据结构和组件参数提供类型约束

Supabase
  └── 保存和读取调研平台数据
```

改成工程化项目后，页面可以拆分成更清晰的模块，例如列表、筛选、详情、表单和导航等；同时也更方便后续连接 Supabase、增加数据管理功能，或扩展不同类型的调研内容。

这一过程也带来了一个比较重要的反思：一开始把需求理解得过于简单，只想用最轻量的方式快速完成。但即使是看起来不复杂的平台，也应该先考虑它后续是否要维护、是否要接数据、是否会增加页面和交互，以及多人或多次迭代时如何保持代码清晰。

```text
先完成一个页面
不等于
完成一个可维护的项目

页面能显示
不等于
数据、结构和后续扩展已经准备好
```

以后面对新的需求时，需要更早建立工程化思维：先判断需求的生命周期和后续变化，再选择合适的技术方案。简单需求可以快速起步，但项目结构、数据边界和可维护性仍然需要提前考虑，而不是等问题变复杂后再被动重构。

## 二、本周感想

本周最大的收获，是开始更加重视“从页面到项目”的区别。

静态 HTML 很适合快速验证页面结构和视觉方向，但当项目需要持续维护、接入数据库、增加交互或扩展多个页面时，工程化结构会更有优势。Next.js、React 和 TypeScript 并不是为了让项目显得复杂，而是为了让后续修改有更清楚的边界：组件放在哪里、数据从哪里来、类型如何约束、页面如何组织。

Supabase 的学习也让我认识到，数据库并不是一个单独放在后端的概念。对于调研平台这类项目，数据模型会直接影响页面如何展示、内容如何维护，以及后续能否方便地进行筛选、查询和更新。先设计好数据表和字段，再连接前端页面，会比把所有内容直接写死在页面中更适合长期维护。

## 三、Go 学习进度

本周开始进行go语言的学习

###  1 ：安装、基础语法与第一个程序

完成 Go 环境和基础命令的学习，了解了 `go run`、`go fmt` 等常用命令，并学习了包、`main` 函数、变量、基本类型和函数。

```go
package main

import "fmt"

func add(a int, b int) int {
    return a + b
}

func main() {
    result := add(3, 4)
    fmt.Println(result)
}
```

Go 的语法比较简洁，例如函数使用 `func` 定义，变量可以使用 `:=` 进行类型推断。第一天的练习方向是完成一个支持加减乘除的命令行计算器，并养成运行 `go fmt` 格式化代码的习惯。

###  2 ：流程控制与集合

学习了 `for`、`if`、`switch` 和 `defer`，以及数组、slice 和 map 的基本使用。

Go 没有传统语言中完全独立的 `while` 关键字，循环主要通过 `for` 完成：

```go
for i := 1; i <= 3; i++ {
    fmt.Println(i)
}
```

`slice` 可以理解为动态长度的数据序列，`map` 则用于保存键值对。通过统计一句话中每个单词出现次数的练习，开始学习如何使用 map 管理和更新数据：

```go
counts := make(map[string]int)

for _, word := range words {
    counts[word]++
}
```

这里的 `range` 用于遍历集合，`_` 表示当前不需要使用索引位置，只关心每一个单词。

###  3 ：结构体、指针和方法

学习了 `struct`、指针和方法。结构体用于将相关数据组织在一起，例如可以定义一本书或一条待办事项：

```go
type Book struct {
    Title  string
    Author string
    Pages  int
}
```

Go 中的指针用于让函数或方法操作原始数据。使用指针接收者时，方法可以修改结构体本身：

```go
func (b *Book) AddPages(pages int) {
    b.Pages += pages
}
```

这一部分让我开始理解“传值”和“传指针”的区别：传值会得到一份副本，适合不需要修改原数据的场景；传指针则可以修改原对象，但也需要更清楚地知道数据会在哪里被改变。

###  4 ：接口与错误处理

学习了 interface、类型断言和 Go 中的 `error` 处理方式。

Go 的接口不需要提前显式声明“某个类型要实现哪个接口”，只要一个类型实现了接口要求的方法，就可以被当作该接口使用：

```go
type Describer interface {
    Describe() string
}

type Center struct {
    Name string
}

func (c Center) Describe() string {
    return "Compute center: " + c.Name
}
```

错误处理方面，Go 通常把错误作为函数的额外返回值显式返回：

```go
func readFile(path string) (string, error) {
    data, err := os.ReadFile(path)
    if err != nil {
        return "", fmt.Errorf("read file %q: %w", path, err)
    }

    return string(data), nil
}
```

调用方需要主动检查 `err`，而不是依赖异常机制自动跳转。这样的写法一开始会感觉代码多一些，但能让错误处理路径直接出现在函数调用附近，也更容易看出哪些步骤可能失败。

我对 Go 的整体特点有了初步感受：语言语法比较直接，强调可读性、明确的数据处理和显式错误处理。接下来会继续学习模块、测试、并发和 HTTP API，将基础语法逐渐连接到实际后端项目中。
