### 项目结构、Docker 与 Rust 的理解

### 1. Blog 项目的重新优化结构

主要在完善个人博客项目，目标不是单纯把页面做得好看一点，而是希望把它整理成一个后续能持续记录、维护和迭代的个人技术博客。

刚开始上手优化的时候，感觉目录结构和页面风格都比较杂。文件虽然不算特别多，但页面、组件、样式、接口和文档混在一起后，后续想改一个功能时不太容易判断应该放在哪里。于是我先从项目结构入手，对目录职责、文件命名和文档位置做了整理。比如把不同应用按职责区分，博客前端、留言板接口、文档和测试分别归类；同时统一了组件、变量和文件的命名方式，这一点也是需要重点培养的习惯，之前写文件代码都是想到取啥名，后面还是要严格遵守命名习惯，让后面自己回来看代码时也能更容易理解。
后续命名需要遵循核心目标是：一致、易读、便于工具处理。常见约定方法像是驼峰命名法（https://zh.wikipedia.org/wiki/%E9%A7%9D%E5%B3%B0%E5%BC%8F%E5%A4%A7%E5%B0%8F%E5%AF%AB）

将原先的 Astro 前端改造为 Vite + React + TypeScript，同时保留 GitHub Pages 静态部署方式：

React 主要负责页面的内容和交互，比如文章列表、文章详情、导航这些页面；Vite 主要负责在本地启动项目和打包发布，所以平时改完代码能比较快看到效果。项目里的文章是用 Markdown 写的，再通过脚本生成网站要用的数据，最后打包成静态网页部署到 GitHub Pages。Vite 的原理可以理解成：把开发和打包这两件事分开，并尽量减少等待。开发时，Vite 会在本地启动一个服务器，把浏览器需要的代码按模块提供出来。修改某个组件后，它会找到这个组件以及相关部分，只更新必要内容，浏览器不需要每次都重新加载整个网站。
### 2. Chatbot 项目的优化结构

#### 2.1 packages 的职责

周二说明之后意识到其实还是有很多的问题存在，像是 `packages/` 下面具体应该是放啥，其实本质上我也不是很清楚。后续再了解之后知道了，一般来说 `packages/` 下应该放的是：多个应用共享的 UI 组件、多个应用共享的 API Client。

它们之间都有一些共同的特征，像是是否被至少两个应用使用，或明确会成为独立能力；有没有稳定的对外 API 接口；是不是能独立版本化和维护。

而我目前项目下的 `packages/` 只有一个模块，它不是共享组件库，而是一个完整的 React/Vite 网站起始模板，Rust API 会读取它的文件内容，用来生成新项目。从职责和依赖关系来看，应该不需要单独保留 `packages/`，因为目前来说只有 Rust API 使用这个模板，它也不需要独立发布。这个模板也不能单独脱离 API 运行，更合理的结构应该是：

```text
apps/api/resources/templates/react-vite/
```

这样更符合“谁拥有、谁维护、谁使用”的原则。

#### 2.2 Docker 的位置和理解

除此之外就是 Docker 的问题，刚开始我对 Docker 的理解比较模糊，只知道它似乎和部署有关，能把程序做成镜像，方便在服务器上运行。最初我将 Docker 放到 `platform` 下面，认为 Docker 只是部署平台的一部分。

但实际上，`Dockerfile`、`compose.yaml` 和 `.dockerignore` 更接近服务本身：它们定义了服务如何构建、依赖什么环境、暴露什么端口、怎样启动。当服务代码发生变化时，Docker 配置往往也需要同步修改。把它放在服务或项目根目录附近，降低遗漏 Docker 构建更新的风险。

后续也是多学习了一下 Docker，Docker 不只是一个方便部署的镜像工具，更重要的是它能把应用的运行环境标准化、可复现化。它把代码、运行时、依赖和启动方式描述清楚，让开发、测试和部署环境尽可能一致。

简单来说，像是我之前启动一个项目需要分别执行：

```bash
cargo run
npm run dev
```

之类的。如果后续还需要加入更多的服务，类似于 PostgreSQL 等等，都是要分别手动启动。使用 Docker Compose 后，可以将这些服务及其网络、端口、环境变量、数据卷统一定义，一条命令启动完整环境。

这也让我理解了为什么 Docker 配置文件应该放在项目根目录，而不是单独放在 `platform` 目录下。

#### 2.3 Docker 应该如何使用
要想使用需要包含以下四个配置分别是：Dockerfile 服务如何构建、如何启动，compose.yaml多个服务如何一键协作启动、.dockerignore哪些文件不应打入镜像、.env / .env.example 运行配置和敏感信息如何管理。（https://docs.docker.com/get-started/docker-overview/）
2.3.1首先是Dockerfile就像是构建说明书，告诉Docker从什么基础环境开始、复制哪些代码、执行哪些构建命令，以及容器启动后运行什么。
以Rust 示例：
```text
# 使用带 Rust 编译器的基础镜像
FROM rust:1.85 AS builder

# 容器内的工作目录
WORKDIR /app

# 复制后端代码
COPY backend/ .

# 编译 Release 可执行文件
RUN cargo build --release

# 第二阶段：使用更小的运行镜像
FROM debian:bookworm-slim

WORKDIR /app

# 只从编译阶段拿最终程序，不带编译器和源码
COPY --from=builder /app/target/release/backend /app/backend

# 程序监听的端口，仅作说明
EXPOSE 8080

# 容器启动时执行的命令
CMD ["/app/backend"]
```
2.3.2compose.yaml就像是系统说明书，把多个容器组织到一起例如：
```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data

  backend:
    build:
      context: .
      dockerfile: backend/Dockerfile
    environment:
      DATABASE_URL: postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}
    ports:
      - "8080:8080"
    depends_on:
      - db

volumes:
  postgres_data:
```
像是这份这份 compose.yaml 定义了一套由 PostgreSQL 和后端服务组成的开发环境：db 服务使用 PostgreSQL 16，并从 .env 读取数据库账号、密码和库名，将电脑的 5432 映射到容器端口，同时通过 postgres_data 卷持久保存数据；backend 服务则根据项目根目录下的 backend/Dockerfile 构建镜像，将电脑的 8080 映射到后端容器的 8080，并使用 DATABASE_URL 通过 Docker 内部服务名 db:5432 连接数据库，depends_on 表示 Compose 会先启动数据库容器再启动后端容器。
2.3.3
.env 与 .env.example不同电脑、不同环境的配置不同；密码更不能写进代码或 Dockerfile。因此使用环境变量。
```text
POSTGRES_USER=appuser
POSTGRES_PASSWORD=your-local-password
POSTGRES_DB=appdb
```
Compose 中的 ${POSTGRES_USER} 会读取这里的值。还有就是.env是自己实际使用的本地配置，记得加入 .gitignore，不能提交
2.3.4.dockerignore
.dockerignore 主要就是告诉Docker哪些文件不要进入镜像，用于排除不该打进镜像的内容：
```text
# Git 与编辑器文件
.git
.gitignore
.vscode
.idea

# 密钥与本地配置
.env
.env.*
#等等...
```
不把 .env、密钥等敏感信息打进镜像，还有就是避免将开发垃圾文件或旧构建产物混入正式镜像。

#### 2.4 Docker 和 PostgreSQL

在了解 Docker 的过程中，我发现它不仅用于打包和部署服务，也很适合快速启动 PostgreSQL 这类开发依赖。以前如果要使用数据库，可能需要在本机单独安装、配置版本和账号密码；而使用 Docker 后，可以通过统一的配置快速启动一个隔离的 PostgreSQL 环境，并通过数据卷保留数据库数据。

Docker 和 PostgreSQL 是相互配合的，Docker 解决 PostgreSQL 的启动、运行环境和版本统一问题，PostgreSQL 则负责业务数据的存储、查询和管理。这也是后续着重学习的方向。

#### 2.5 caddy
对Caddy进行了一些了解（https://zh.wikipedia.org/wiki/Caddy）（https://caddyserver.com/docs/）
Caddy是一个Web 服务器和反向代理工具。它通常部署在业务服务之前，对外负责域名访问、HTTPS、安全连接和请求转发；后端应用只需要专注业务逻辑，例如运行在 8080、3000 之类的内部端口。
我认为 Caddy 最突出的作用是用较少配置得到正确的默认结果。传统方案里，配置 HTTPS 往往还要额外申请证书、编写续期脚本、处理 HTTP 跳转和重载服务；Caddy 把这些整合为默认能力。只要域名解析正确、80 和 443 端口开放，它通常可以自动申请和续期证书。
与 Nginx 相比，Caddy 的优势在于配置更简洁、自动 HTTPS 体验更好、适合快速上线和日常维护。Nginx 的优势则是生态成熟、资料丰富、并发等，如果是小中型项目、独立服务、快速部署的话我认为可以优先考虑 Caddy。
还需要了解一下Cadyy一些基础配置，像是本项目也有用写到的配置反向代理:
```
http://example.localhost {
	handle /api/* {
		reverse_proxy 127.0.0.1:4173
	}

	handle /healthz {
		reverse_proxy 127.0.0.1:4173
	}

	handle {
		reverse_proxy 127.0.0.1:3000
	}
}

http://*.example.localhost {
	reverse_proxy 127.0.0.1:4173
}
```
简单来说，Caddy 在这里相当于一个本地流量分发器：主域名下的 API 和健康检查请求去 4173，普通页面请求去 3000，而所有子域名请求统一去 4173。其中 reverse_proxy 就是反向代理，浏览器以为自己访问的是 example.localhost，实际上 Caddy 在后台替它访问了 127.0.0.1:3000 或 127.0.0.1:4173。
除此之外Caddy还有一些常用功能的配置例如：
多服务负载均衡
```
api.example.com {
    reverse_proxy 127.0.0.1:8081 127.0.0.1:8082 127.0.0.1:8083 {
        lb_policy round_robin
        health_uri /actuator/health
    }
}
```
Caddy 会以轮询方式向多个后端实例分发请求，并检查健康状态。
使用已有 HTTPS 证书,本地或内网 HTTPS等。

### 3. Rust 的理解

Rust 虽然说是过了一遍，但是也是一知半解，这几天也是一直在思考 Rust 的特质是啥，和其他语言的区别是啥。也是一遍学习一遍思考，在继续学习的过程中，我开始把 Rust 和自己比较熟悉的 C++ 放在一起思考。两者都强调性能，也都可以用于系统编程，但它们在内存管理和并发安全方面采取了不同的思路。

我注意到以下几个问题的区别。

#### 内存泄漏

像是内存泄漏问题，程序申请了一块内存，但后来找不到它了，也没有释放它。在 C++ 中：

```cpp
void work() {
    int* p = new int(42);
}
```

`p` 是一个指针变量，函数结束后指针没了，但堆上的 `42` 还占着内存。反复调用 `work()`，内存会越来越少。正确的写法应该是要加上 `delete`，但人工 `delete` 很容易漏掉、重复释放，或者在异常路径下没有执行。

在 Rust 中：

```rust
fn work() {
    let value = Box::new(42);
}
```

当 `value` 离开作用域时，Rust 自动释放 `Box` 里的内存。这就涉及到 Rust 自身的特殊默认规则了，在生命周期结束的时候释放数据。我觉得这也算是 Rust 严谨的一个特性，Rust 能避免大多数由忘记释放造成的内存泄漏。

#### 使用已释放内存

除此之外还有类似于使用已释放内存，像是 C++：

```cpp
int* p = new int(42);
delete p;

std::cout << *p;
```

使用已释放内存，它可能打印垃圾值，也可能直接崩溃。

但是在 Rust：

```rust
let value = Box::new(42);
drop(value);

println!("{value}");
```

直接会编译错误，Rust 知道 `value` 已经被销毁，因此禁止再次使用。

#### 数据竞争

还有就是数据竞争的问题，多个线程同时访问同一份数据时，其中至少有一个线程会修改数据，而访问过程又没有经过正确同步。

```cpp
int counter = 0;

void add() {
    counter = counter + 1;
}

thread1(add);
thread2(add);
```

表面上看，两个线程各自加一次，结果应该是 `2`。但实际上，最终结果可能只有 `1`，多个线程执行这些步骤时，顺序可能交错。由于线程调度是不确定的，这种问题有时出现，有时不出现，因此非常难以测试和定位。

在 C++ 中，这种问题一般的解法是加锁，需要自己使用互斥锁来解决，但是是否安全主要依赖程序自己判断。如果忘记加锁，或者某个代码路径没有正确加锁，编译器通常不会主动阻止。

Rust 则会限制这种行为，像是：

```rust
use std::thread;

fn main() {
    let mut counter = 0;

    thread::scope(|scope| {
        scope.spawn(|| {
            counter += 1;
        });

        scope.spawn(|| {
            counter += 1;
        });
    });
}
```

Rust 会拒绝这段代码，因为两个线程都想获得 `counter` 的可变访问权。编译器无法确认它们之间是否安全，因此直接报错。如果 Rust 程序确实需要让多个线程共享并修改数据，就必须明确使用同步工具：`Arc` 和 `Mutex`。当初看到并发章节的时候也是不太理解这些为啥要这么写，现在也是有点理解了。（https://rustwiki.org/zh-CN/book/ch16-03-shared-state.html?highlight=Arc#mutex%E7%9A%84-api）

因此，Rust 并不是禁止多线程共享数据，而是要求明确表达共享和修改的方式。

所以 Rust 语言来说不是绝对不会出错，而是把很多 C++ 中要靠经验、规范和代码审查保证的问题，提前变成了编译器可以检查的问题。从而规避掉一些在真实生产环境下才会暴露的问题。
