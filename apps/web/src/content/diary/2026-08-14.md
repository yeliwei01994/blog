### 项目结构、Docker 与 Rust 的理解

### 1. Blog 项目的重新优化结构

主要在完善个人博客项目，目标不是单纯把页面做得好看一点，而是希望把它整理成一个后续能持续记录、维护和迭代的个人技术博客。

刚开始上手优化的时候，感觉目录结构和页面风格都比较杂。文件虽然不算特别多，但页面、组件、样式、接口和文档混在一起后，后续想改一个功能时不太容易判断应该放在哪里。于是我先从项目结构入手，对目录职责、文件命名和文档位置做了整理。比如把不同应用按职责区分，博客前端、留言板接口、文档和测试分别归类；同时统一了组件、变量和文件的命名方式，这一点也是需要重点培养的习惯，之前写文件代码都是想到取啥名，后面还是要严格遵守命名习惯，让后面自己回来看代码时也能更容易理解。

优化后结构：

```text
astro-blog/
├─ apps/
│  ├─ web/                # 博客前端
│  │  ├─ src/
│  │  │  ├─ content/      # 日记内容
│  │  │  ├─ features/     # 首页、日记、留言板功能
│  │  │  ├─ layouts/      # 页面布局
│  │  │  ├─ pages/        # 路由页面
│  │  │  ├─ site/         # 页头、页脚等通用组件
│  │  │  └─ styles/       # 样式
│  │  └─ tests/           # 前端测试
│  │
│  └─ guestbook-api/      # 留言板后端
│     └─ src/
│
├─ docs/                  # 架构、设计与历史文档
├─ .github/               # 自动部署
├─ README.md              # 项目说明
└─ AGENTS.md              # 开发协作说明
```

之后又对页面设计进行一些改进，之前的页面存在几个比较明显的问题比如标题太大，正文区域偏挤，目录和正文的关系不够清楚，而且一些装饰性内容会影响阅读节奏。重新做了一版页面布局让阅读体验更好了一点。

### 2. Chatbot 项目的优化结构

#### 2.1 packages 的职责

周二说明之后意识到其实还是有很多的问题存在，像是 `packages/` 下面具体应该是放啥，其实本质上我也不是很清楚。后续再了解之后知道了，一般来说 `packages/` 下应该放的是：多个应用共享的 UI 组件、多个应用共享的 API Client。

它们之间都有一些共同的特征，像是是否被至少两个应用使用，或明确会成为独立能力；有没有稳定的对外 API 接口；是不是能独立版本化和维护。

而我目前项目下的 `packages/` 只有一个模块，它不是共享组件库，而是一个完整的 React/Vite 网站起始模板，Rust API 会读取它的文件内容，用来生成新项目。从职责和依赖关系来看，应该不需要单独保留 `packages/`，因为目前来说只有 Rust API 使用这个模板，它也不需要独立发布。这个模板也不能单独脱离 API 运行，更合理的结构应该是：

```text
apps/api/resources/templates/react-vite/
```

这样更符合“谁拥有、谁维护、谁使用”的原则。

#### 2.2 Docker 的位置和理解

除此之外就是 Docker 的问题，刚开始我对 Docker 的理解比较模糊，只知道它似乎和部署有关，能把程序做成镜像，方便在服务器上运行。最初我将 Docker 放到 `platform` 下面，认为 Docker 只是部署平台的一部分。

但实际上，`Dockerfile`、`compose.yaml` 和 `.dockerignore` 更接近服务本身：它们定义了服务如何构建、依赖什么环境、暴露什么端口、怎样启动。当服务代码发生变化时，Docker 配置往往也需要同步修改。把它放在服务或项目根目录附近，降低遗漏 Docker 构建更新的风险。

后续也是多学习了一下 Docker，Docker 不只是一个方便部署的镜像工具，更重要的是它能把应用的运行环境标准化、可复现化。它把代码、运行时、依赖和启动方式描述清楚，让开发、测试和部署环境尽可能一致。

简单来说，像是我之前启动一个项目需要分别执行：

```bash
cargo run
npm run dev
```

之类的。如果后续还需要加入更多的服务，类似于 PostgreSQL 等等，都是要分别手动启动。使用 Docker Compose 后，可以将这些服务及其网络、端口、环境变量、数据卷统一定义，一条命令启动完整环境。

这也让我理解了为什么 Docker 配置文件应该放在项目根目录，而不是单独放在 `platform` 目录下。

优化后的项目结构：

#### 2.3 Docker 和 PostgreSQL

在了解 Docker 的过程中，我发现它不仅用于打包和部署服务，也很适合快速启动 PostgreSQL 这类开发依赖。以前如果要使用数据库，可能需要在本机单独安装、配置版本和账号密码；而使用 Docker 后，可以通过统一的配置快速启动一个隔离的 PostgreSQL 环境，并通过数据卷保留数据库数据。

Docker 和 PostgreSQL 是相互配合的，Docker 解决 PostgreSQL 的启动、运行环境和版本统一问题，PostgreSQL 则负责业务数据的存储、查询和管理。这也是后续着重学习的方向。

### 3. Rust 的理解

Rust 虽然说是过了一遍，但是也是一知半解，这几天也是一直在思考 Rust 的特质是啥，和其他语言的区别是啥。也是一遍学习一遍思考，在继续学习的过程中，我开始把 Rust 和自己比较熟悉的 C++ 放在一起思考。两者都强调性能，也都可以用于系统编程，但它们在内存管理和并发安全方面采取了不同的思路。

我注意到以下几个问题的区别。

#### 内存泄漏

像是内存泄漏问题，程序申请了一块内存，但后来找不到它了，也没有释放它。在 C++ 中：

```cpp
void work() {
    int* p = new int(42);
}
```

`p` 是一个指针变量，函数结束后指针没了，但堆上的 `42` 还占着内存。反复调用 `work()`，内存会越来越少。正确的写法应该是要加上 `delete`，但人工 `delete` 很容易漏掉、重复释放，或者在异常路径下没有执行。

在 Rust 中：

```rust
fn work() {
    let value = Box::new(42);
}
```

当 `value` 离开作用域时，Rust 自动释放 `Box` 里的内存。这就涉及到 Rust 自身的特殊默认规则了，在生命周期结束的时候释放数据。我觉得这也算是 Rust 严谨的一个特性，Rust 能避免大多数由忘记释放造成的内存泄漏。

#### 使用已释放内存

除此之外还有类似于使用已释放内存，像是 C++：

```cpp
int* p = new int(42);
delete p;

std::cout << *p;
```

使用已释放内存，它可能打印垃圾值，也可能直接崩溃。

但是在 Rust：

```rust
let value = Box::new(42);
drop(value);

println!("{value}");
```

直接会编译错误，Rust 知道 `value` 已经被销毁，因此禁止再次使用。

#### 数据竞争

还有就是数据竞争的问题，多个线程同时访问同一份数据时，其中至少有一个线程会修改数据，而访问过程又没有经过正确同步。

```cpp
int counter = 0;

void add() {
    counter = counter + 1;
}

thread1(add);
thread2(add);
```

表面上看，两个线程各自加一次，结果应该是 `2`。但实际上，最终结果可能只有 `1`，多个线程执行这些步骤时，顺序可能交错。由于线程调度是不确定的，这种问题有时出现，有时不出现，因此非常难以测试和定位。

在 C++ 中，这种问题一般的解法是加锁，需要自己使用互斥锁来解决，但是是否安全主要依赖程序自己判断。如果忘记加锁，或者某个代码路径没有正确加锁，编译器通常不会主动阻止。

Rust 则会限制这种行为，像是：

```rust
use std::thread;

fn main() {
    let mut counter = 0;

    thread::scope(|scope| {
        scope.spawn(|| {
            counter += 1;
        });

        scope.spawn(|| {
            counter += 1;
        });
    });
}
```

Rust 会拒绝这段代码，因为两个线程都想获得 `counter` 的可变访问权。编译器无法确认它们之间是否安全，因此直接报错。如果 Rust 程序确实需要让多个线程共享并修改数据，就必须明确使用同步工具：`Arc` 和 `Mutex`。当初看到并发章节的时候也是不太理解这些为啥要这么写，现在也是有点理解了。

因此，Rust 并不是禁止多线程共享数据，而是要求明确表达共享和修改的方式。

所以 Rust 语言来说不是绝对不会出错，而是把很多 C++ 中要靠经验、规范和代码审查保证的问题，提前变成了编译器可以检查的问题。从而规避掉一些在真实生产环境下才会暴露的问题。
