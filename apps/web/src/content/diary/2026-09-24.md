## 了解几起生产事故后的反思

昨天写完两起事故的反思后，我又找了一些公开的生产事故复盘看。之前我对生产事故的理解比较简单，觉得大多是代码有问题，或者操作的时候不小心。看完这些案例后发现，事故往往不是某一个环节单独出错，而是环境判断、操作确认、代码检查、测试和异常处理多个环节连续出现问题，最后才造成比较大的影响。

### 1. GitLab 误删主数据库

2017 年，GitLab 的工程师在处理数据库同步问题。当时主数据库和备用数据库之间的同步出现延迟，需要重新同步备用数据库。按正常操作，需要先清空备用数据库的数据目录，再从主数据库复制数据。

工程师在备用数据库上清理目录并启动复制后，程序没有很明显的输出。因为不清楚程序实际在等待什么，团队尝试排查复制为什么没有继续。过程中还遇到了数据库连接数不足、数据库重启失败等问题，相关人员尝试调整数据库配置，但问题仍然没有解决。由于操作说明没有把复制程序的等待行为解释清楚，工程师怀疑目录里还有残留文件，于是又准备清理一次。

这一次清理时，操作目标弄错了，命令执行在主数据库上。工程师发现不对后马上停止，但主库中约 300 GB 的数据已经被删除大部分。之后团队尝试寻找备份，但备份恢复流程也没有按预期工作，最后只能使用较早的数据副本恢复。GitLab.com 因此中断约 18 个小时，部分数据库数据没有恢复，受影响的内容包括项目、评论、用户账号等。

这起事故还要再次确认我现在操作的是哪台机器。当时工程师本来要清理备用数据库，却误操作到主数据库。我前天把服务器当成普通测试环境来操作，虽然没有改动数据，但也是没有确认清楚当前服务器的用途和状态。两种情况的后果不同，但都提醒我，不能靠自己的印象判断环境，更不能觉得操作内容简单就省掉确认步骤。

### 2. Knight Capital 一台服务器没有更新，旧代码被触发

Knight Capital 是一家金融交易公司。2012 年，公司为了支持一项新的交易功能，对自动交易系统进行了代码更新。系统一共有八台服务器，部署新代码时，其中七台完成了更新，但有一台没有复制到新代码。旧代码仍留在这台服务器上，也没有第二个人检查部署结果，所以当时没有人发现服务器之间的代码版本不一致。

问题是，新代码使用了一个以前就存在的标记位。更新完成的服务器会把这个标记位识别为新功能，那台没有更新的服务器却仍把它当成旧功能的启动标记。旧功能虽然已经多年没有使用，但代码还留在系统中，而且以前调整过相关逻辑，没有再经过完整测试。

市场开盘后，订单进入这台没有更新的服务器，旧功能被触发。系统没能正确识别订单已经完成，持续向市场发送更多子订单。45 分钟内，系统对 212 个客户订单发出了数百万笔错误交易，涉及 154 只股票。Knight Capital 因此积累了大量非预期的交易头寸，最终损失超过 4.6 亿美元。

事故发生前，系统已经发送过一些错误邮件，其中包括旧功能被禁用之类的信息，但这些邮件没有被当作需要立即处理的告警，所以没有人在市场开盘前及时发现问题。美国证券交易委员会的调查还指出，公司没有足够的代码部署复核和异常停止机制。

这个案例让我对代码合并和部署有了更具体的认识。代码合并了，不代表所有服务器都已经更新，部署完成了，也不代表每个环境运行的都是同一份代码。我的代码合并事故虽然没有造成这种程度的影响，但如果仓库里进入了不符合预期的代码，后续又有人在这个基础上继续开发，问题就会越来越难定位。因此，合并前需要核对分支和具体改动，合并后也应该检查实际结果，不能只看操作有没有成功。

### 3. Cloudflare 的安全规则测试通过，仍然造成全球服务故障

2019 年，Cloudflare 更新了一条用于识别网络攻击的 WAF 安全规则。这次变更提交了 Pull Request，经过审批，自动化测试也通过了。之后系统按照当时的流程自动部署了新规则。

问题出在规则中使用的正则表达式。遇到某些请求内容时，正则表达式需要进行大量重复匹配和回溯，导致 CPU 资源被迅速耗尽。规则即使处于模拟模式，也仍然要处理真实流量，只是不会拦截请求，因此模拟模式并没有避免 CPU 消耗问题。

新规则发布后，Cloudflare 处理 HTTP/HTTPS 流量的服务器 CPU 使用率迅速升高，全球多个地区的服务受到影响，访问 Cloudflare 所代理网站的用户看到了大量 502 错误。事故持续了约 27 分钟。团队发现 WAF 是问题来源后，执行了全局关闭该组件的操作，流量和 CPU 使用情况随后恢复。恢复 WAF 前，团队先在一个城市、少量流量上检查问题原因和回滚结果，确认后才重新启用。

这次事故还有一个比较值得注意的地方，Cloudflare 自己的部分内部工具也依赖其服务。故障期间，团队访问内部控制面板和一些工作工具时遇到了问题，最后需要使用不常用的备用方式完成操作。也就是说，修复生产故障所需要的工具，本身也可能受到故障影响。

这个案例说明，审批和自动化测试只能证明已有流程检查过的内容没有发现问题，不代表所有风险都已经排除。Cloudflare 的测试检查了规则是否能正常识别请求，却没有发现它会消耗过多 CPU。我以后看代码合并结果时，还要了解改动具体做了什么，如果部署或合并的影响范围不清楚，就先问清楚再继续。

### 4. AWS S3 操作参数输入错误，移除了过多服务器

2017 年，AWS 的工程师在排查 S3 计费系统处理缓慢的问题。工程师按照既有操作手册执行命令，本来只打算移除少量与计费相关的服务器，但命令中的一个输入填错了，实际移除的服务器数量比预期多。

这些服务器还支撑着 S3 的索引和存储分配功能。索引功能负责记录对象的位置等信息，S3 需要它才能正常处理用户的读写请求。移除过多服务器后，相关子系统需要整体重启。恢复过程中，S3 在美国东部区域一度无法正常提供服务，依赖 S3 的其他 AWS 服务也受到影响。

事故发生后，S3 的部分请求能力开始逐步恢复，但完整恢复花了数小时。AWS 复盘认为，虽然工程师使用了既有操作手册，但当时的工具允许一次移除过多容量。之后 AWS 调整了工具，让移除容量的速度变慢，并增加了最低容量保护，避免系统容量降到无法正常运行的程度。

这个事故让我认识到，照着操作手册做也不一定就安全，命令里的目标和参数仍然需要核对。对于有风险的操作，最好不要只依赖操作者自己记住每一步，还要有工具上的限制和操作后的检查。我在服务器上部署代码之前，也应该再看一遍目标环境、代码来源和操作范围；如果发现不确定的地方，就先停下来确认。

### 5. 看完这些案例后的想法

这几起事故里，有的是把主库和备用库弄错，有的是漏更新了一台服务器，有的是测试没有发现代码的资源消耗问题，还有的是命令参数输错后一次移除了过多服务器。它们的严重程度和我自己的事故不一样，但事故经过让我看到，很多问题都发生在以为自己已经确认了的时候，最终造成了T0级别的事故。

我昨天没有确认服务器已经进入内测，也没有确认把本地代码部署上去是否符合当前安排，代码合并时，我也没有把合并内容、分支和预期结果核对清楚。沟通不清确实是背景之一，但我应该主动把不清楚的地方问出来，而不是按自己的理解继续操作。

以后涉及服务器部署和代码合并，我会先确认目标环境、操作内容和影响范围，再开始操作。完成之后也要检查服务器或仓库里的实际结果是否符合预期。遇到目标不清楚、代码范围有疑问或者结果不对的时候，我会先停下来确认，不继续往下做。

看这些事故案例对我来说不是为了把自己的问题说得很严重，而是让我更清楚地看到，如果生产操作中的小问题没有被及时发现，后面可能会怎样扩大。之后我会继续看一些和部署、环境确认、代码合并有关的事故复盘，结合自己这次遇到的问题，把该确认的事情真正落实到操作之前和操作之后。



### 6. 学习网页设计

本周我还了解一下网页设计相关内容，给了 Tesla、OpenAI、Apple 和 Claude Code 这几个网站作为参考。我以前看网页时比较关注整体好不好看，这次我试着多看了一下页面是怎么安排内容的，用户打开后先看到什么，怎么从一个页面区域看到下一个区域，产品特点和操作入口又是怎么放在一起的。

#### Tesla

我先看了 Tesla 的官网和 Model 3 产品页。页面一开始就把车型和主要入口放出来，用户可以直接选择订购或了解更多。往下浏览时，再看到续航、外观、内饰等具体内容。它没有一开始就把所有参数都塞到用户面前，而是先让人知道这是什么产品，再一段一段补充信息。

我觉得 Tesla 的页面比较适合学习产品介绍和购买流程怎么结合。每一段介绍完产品特点，都会有继续了解或订购的入口，用户不用看完一大堆内容之后再回到页面顶部找按钮。以后做产品页面时，我也应该先想清楚用户最需要了解什么，哪些信息应该先出现，哪些操作需要让用户随时能找到。

#### OpenAI

我看的是 ChatGPT 的产品介绍页。页面先把 Chat、Work、Codex 分开介绍，每一块对应的用途不一样。之后又继续展示写作、图片、工作和编程等场景。这样安排下来，页面不是从技术功能开始逐项解释，而是先告诉用户可以用它做什么，再用具体例子帮助理解。

我觉得这种写法比较容易看懂。一个产品有很多功能时，如果把功能名字全部排列出来，用户可能还是不知道它和自己有什么关系。OpenAI 的页面会把功能放到使用场景里介绍，让人能对应到自己的需求。做页面时可以先从用户的问题出发，再讲产品功能，而不是先讲一堆功能名。

#### Apple

Apple 的 iPhone 页面内容比较多，但它把相机、芯片、电池、设计等内容分成了不同部分。每个部分围绕一个主题展开，配上对应的产品图片和简短说明。页面继续往下看时，可以接着了解其他功能，最后再看到不同型号的产品和比较、购买等入口。

我注意到它不会在一个区域里同时讲很多件事，而是尽量让每一段内容只突出一个重点。大图和短文字一起出现，让用户先看到产品，再读这个部分要说明的功能。页面内容虽然长，但因为主题分得比较清楚，不容易感觉所有信息都挤在一起。这让我想到，页面的内容多不一定就要做得很乱，重要的是每一块讲什么要明确，用户浏览时能知道自己正在看哪部分。

#### Claude Code

Claude Code 的页面面向开发者，开头直接介绍它能帮忙处理的问题，比如修复 bug、写测试、迁移代码等。页面里展示了终端和代码修改过程，也把它可以使用的环境和入口列出来，例如终端、网页、IDE 等。后面还用具体开发任务说明它会怎样查看代码、分析问题、修改文件。

我觉得这个页面和前面几个产品页的区别是，它更注重展示实际工作过程。开发工具如果只写“支持代码分析”或“可以辅助开发”，不太容易让人想象它具体怎么用。页面直接把一个任务和处理过程展示出来，用户就能更快明白工具能做什么。以后介绍功能时，也可以多想想能不能用真实场景说明，而不是只写一句功能描述。



看完这几个网站，网页设计不是只调颜色、字号和间距。页面里先放什么内容、信息怎么分组、图片是否能帮助说明功能、用户下一步能做什么，这些都和设计有关。真正的核心我觉得就是以**用户的视角出发**，还有就是平时多提升一下审美吧，虽然这时代AI设计横行，但是不同审美通过AI做出来的设计也是差距很大的。
