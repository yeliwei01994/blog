### Redis：缓存、数据结构与可靠性

#### Redis 是什么
Redis 是一个开源、基于内存的键值型数据库，也可以称为内存数据结构服务。它以 Key-Value 的形式保存数据。

可以先把它理解成：**用 Key 找 Value 的内存数据库**。因为数据主要放在内存中，读写速度很快，所以经常被用作缓存，减少应用程序对 MySQL 等数据库的访问压力。

Redis 不只支持简单字符串，还内置了多种数据结构：

| 数据结构 | 特点 | 常见场景 |
|:---|:---|:---|
| String | 字符串 | Token、验证码、计数器、JSON |
| Hash | 哈希 | 保存对象的多个字段 |
| List | 有序且允许重复 | 队列、栈、消息列表 |
| Set | 自动去重 | 标签、交并差集 |
| Sorted Set | 带分数的有序集合 | 排行榜、排序 |
| Stream | 消息流 | 消息队列、事件记录 |

##### Redis 作为缓存

假设维护了一个商品服务，它背后直连 MySQL：商品服务每秒需要对外提供 `1w` 次查询，但 MySQL 只能承受每秒约 `5k` 次查询。这类大流量查询场景很常见，这时候加一层 Redis 就能分担数据库压力。

查询内存比查询磁盘快。MySQL 的数据主要在磁盘中，如果将热点数据放进内存，很多查询就不需要再走磁盘。当用户查询商品时，程序可以先查询 Redis：
```
用户请求
   ↓
查询 Redis
   ↓
缓存命中：直接返回
   ↓
缓存未命中：查询 MySQL
   ↓
将查询结果写入 Redis
```

除此之外，Redis 还可以保存登录状态和 Token，并设置过期时间；也能快速实现访问量、点赞数、库存数量等计数功能。使用 List 还能实现简单任务队列。

##### 为什么速度快

主要有几个原因：

1. 数据主要保存在内存中，减少磁盘 I/O。
2. Redis 内置了多种高效数据结构。
3. 命令执行模型较简单，核心命令通常通过事件循环处理。
4. 使用轻量级通信协议。
5. 很多常用操作的时间复杂度较低，例如 `GET`、`SET` 通常是 `O(1)`。

一些常用命令：
| 命令 | 作用 |
|:---|:---:|
| `PING` | 检查 Redis 是否正常连接 |
| `SET` | 保存字符串数据 |
| `GET` | 获取字符串数据 |
| `EXISTS` | 判断 Key 是否存在 |
| `TYPE` | 查看 Value 的数据类型 |
| `DEL` | 删除 Key |

#### 基础数据：String、Hash 与缓存使用
Redis 的数据通过 Key-Value 形式保存：Key 用于查找数据，Value 用于保存具体内容。例如 `user:1001:name` 是 Key，`张三` 是 Value。

Key 通常使用冒号命名，例如 `user:1001:name`、`article:1001:views`、`login:code:13800138000`。这样能体现数据的业务含义，也方便后续管理。

##### String：保存简单值与计数

String 是最基本的数据类型，可以保存普通文本、数字、Token、验证码和 JSON 字符串等内容。通过 `SET` 保存数据，`GET` 读取数据：
```redis
SET user:1001:name "张三"
GET user:1001:name
```
执行后可以读取到“张三”。如果对同一个 Key 再次执行 SET，新的值会覆盖旧的值：
```redis
SET user:1001:name "李四"
GET user:1001:name
```
最终结果为“李四”。如果需要同时读取多个 Key，可以使用 MGET：
```redis
SET user:1001:age 20
SET user:1001:city "深圳"
MGET user:1001:name user:1001:age user:1001:city
```
MGET 可以一次获取多个 Key，减少客户端与 Redis 之间的网络交互次数。
Redis 还可以对保存为数字的 String 进行自增操作。例如实现文章阅读量统计：
```redis
SET article:1001:views 0
INCR article:1001:views
INCRBY article:1001:views 10
GET article:1001:views
```
其中 INCR 表示自增 1，INCRBY 表示按照指定数值增加。执行完成后，阅读量会从 0 增加到 11。Redis 的这种计数操作可以应用于文章阅读量、点赞数、接口访问次数等场景。如果 Key 中保存的不是数字，例如保存的是“张三”，则不能使用 INCR 进行增加。
##### 过期时间

缓存数据通常不应该永久保存，因此 Redis 支持设置过期时间。例如保存一个 60 秒后失效的验证码：
```redis
SET login:code:13800138000 "9527" EX 60
TTL login:code:13800138000
```
`EX 60` 表示过期时间为 60 秒，`TTL` 用于查看剩余秒数：

- 正数：Key 还存在，并且有对应的剩余时间；
- `-1`：Key 存在，但没有设置过期时间；
- `-2`：Key 不存在或已经过期。

也可以分两步设置过期时间：
```redis
SET product:1001 "手机"
EXPIRE product:1001 30
TTL product:1001
```
这表示商品缓存保存 30 秒。过期时间结束后，Redis 会自动删除这个 Key。

##### Hash：保存对象字段

String 适合保存一个简单值，而 Hash 适合保存一个对象的多个字段。使用 Hash 保存用户信息时，可以执行：
```redis
HSET user:1001 name "张三"
HSET user:1001 age 20
HSET user:1001 city "北京"
```
这里的 user:1001 是 Redis 的 Key，name、age 和 city 是 Hash 内部的字段。可以使用 HGET 获取某一个字段，可以使用 HMGET 一次获取多个字段，如果想查看整个 Hash，可以使用 HGETALL。
需要注意，HGETALL 会返回这个 Hash 中的全部字段。如果一个 Hash 中保存了很多字段，一次性获取全部内容可能会产生较大的网络开销，因此实际开发中应该根据需要使用 HGET 或 HMGET。删除 Hash 中的字段可以使用 HDEL。Hash 也支持对数字字段进行增加。例如统计用户积分：
```redis
HSET user:1001 score 100
HINCRBY user:1001 score 10
HGET user:1001 score
```
HINCRBY 适合用于积分、余额、数量等数字字段的增加。
String 和 Hash 都可以保存对象，但使用方式不同。使用多个 String 保存用户信息时，需要创建多个 Key；而 Hash 一条指令就可以解决：
```redis
HSET user:1001 name "张三" age 20 city "北京"
```
因此，当一个对象包含多个相关字段时，Hash 通常更直观，也更方便统一管理。不过 Hash 的过期时间是设置在整个 Key 上的，不能直接给某一个普通字段单独设置过期时间。

#### 队列、集合与排序
这一部分主要包括 List、Set、Sorted Set 和 HyperLogLog：

| 类型 | 特点 | 适合场景 |
|:---|:---|:---|
| List | 有序、允许重复 | 队列、栈、消息列表、最近访问记录 |
| Set | 无序、自动去重 | 标签、交集、并集、差集 |
| Sorted Set | 成员不重复，并按分数排序 | 排行榜、排序场景 |
| HyperLogLog | 低内存的基数估算 | UV、关键词数、设备数 |

##### List：队列与栈

List 是一种有序且允许重复元素的数据结构。使用 `RPUSH` 从右侧添加元素，使用 `LPOP` 从左侧取出元素：
```redis
DEL task:queue
RPUSH task:queue "task-1"
RPUSH task:queue "task-2"
RPUSH task:queue "task-3"
LRANGE task:queue 0 -1
LPOP task:queue
```
执行 LRANGE task:queue 0 -1 可以查看整个列表，结果为 task-1、task-2、task-3。执行 LPOP 后会取出并删除最左侧的 task-1。使用 RPUSH 添加、LPOP 取出，可以实现先进先出的队列；使用 LPUSH 添加、LPOP 取出，则可以实现后进先出的栈。LLEN 可以查看列表长度，BLPOP 可以在列表为空时等待新任务，适合实现简单的任务消费功能。
##### Set：自动去重与集合运算

Set 是一种无序且不允许重复元素的数据结构。使用 `SADD` 添加元素：
```redis
DEL user:1001:tags
SADD user:1001:tags "redis"
SADD user:1001:tags "mysql"
SADD user:1001:tags "redis"
SMEMBERS user:1001:tags
```
虽然 redis 被添加了两次，但 Set 中只会保存一份，因为 Set 会自动去重。使用 SCARD 可以查看集合元素数量，使用 SREM 可以删除指定元素。Set 的一个重要特点是支持集合运算。例如有两个用户的兴趣标签：
```redis
SADD user:1001:tags "redis" "mysql" "rust"
SADD user:1002:tags "redis" "java" "python"
```
使用 SINTER 查询两个集合的交集，使用 SUNION 查询并集。使用 SDIFF 查询差集。
##### Sorted Set：带分数的排序集合

Sorted Set，也叫 ZSet，是一种有序集合。它和 Set 一样不允许成员重复，但每个成员都会关联一个分数，Redis 会按照分数进行排序。可以使用 `ZADD` 添加排行榜数据：
```redis
DEL game:ranking
ZADD game:ranking 98 "张三"
ZADD game:ranking 95 "李四"
ZADD game:ranking 100 "王五"
```
ZREVRANGE 按照分数从高到低返回结果，WITHSCORES 表示同时返回分数。结果类似：
```redis
ZREVRANGE game:ranking 0 -1 WITHSCORES
王五
100
张三
98
李四
95
```
`ZRANGE` 可以按照从低到高排序，可以使用 `ZSCORE` 查询某个成员的分数，也可以使用 `ZINCRBY` 增加成员分数。

##### HyperLogLog：只关心数量时

HyperLogLog 是 Redis 提供的一种基数统计结构，主要用于统计大量数据中不同元素的数量。例如统计网站一天的独立访客数量：
```redis
PFADD website:uv "user-1001"
PFADD website:uv "user-1002"
PFADD website:uv "user-1001"
PFCOUNT website:uv
```
由于 user-1001 被重复添加，PFCOUNT 统计出的独立用户数量是 2，而不是 3。HyperLogLog 不会保存具体的用户列表，只会对不同元素的数量进行估算，因此占用内存很小，适合统计网站 UV、搜索关键词数量和不同设备数量等场景。
HyperLogLog 的优点是节省内存，缺点是统计结果是估算值，并且不能查看具体有哪些元素。如果业务需要准确保存成员信息，就应该使用 Set；如果只关心不同元素的数量，可以使用 HyperLogLog。
简单总结一下：List 适合队列和栈；Set 适合交集、并集、差集和共同数据计算；Sorted Set 适合排行榜和排序场景；HyperLogLog 适合对大量数据进行低内存的基数统计。

#### Redis 消息与原子操作
这一部分主要包括发布订阅、Stream、事务、Pipeline 和 Lua 脚本，分别用于消息传递、任务处理、批量操作，以及保证多个命令按照整体逻辑执行。

##### 发布订阅与 Stream

Redis 发布订阅功能由发布者、频道和订阅者组成。订阅者先订阅一个频道：
```redis
SUBSCRIBE news
```
执行后，当前客户端会进入等待消息状态。此时需要打开另一个 PowerShell 窗口，进入 Redis 后执行：
```redis
PUBLISH news "test"
```
订阅者窗口会收到消息。PUBLISH 的返回值表示当前有多少个订阅者收到了消息。发布订阅适合实现实时通知、聊天室消息、配置更新通知等功能。但是它不会保存历史消息，如果订阅者发布消息时没有在线，就无法收到之前的消息，因此不适合要求消息可靠保存的任务。
Stream 是 Redis 提供的消息流数据结构，适合保存消息并支持后续读取。可以使用 XADD 添加消息：
```redis
XADD order:stream * user_id 1001 amount 2999
XADD order:stream * user_id 1002 amount 1999
```
其中 `*` 表示让 Redis 自动生成消息 ID。查看 Stream 中的消息：
```redis
XRANGE order:stream - +
```
`-` 表示从最早的消息开始，`+` 表示读取到最后一条消息。Stream 会保存消息内容，因此与发布订阅相比更加可靠，适合订单事件、日志记录和消息队列等场景。Stream 还支持消费者组，可以让多个消费者共同处理消息，适合实际项目中的异步任务处理。

##### 事务、Pipeline 与 Lua

Redis 事务可以将多个命令放入一个事务中执行。使用 `MULTI` 开始事务，后续命令会先进入队列，使用 `EXEC` 后才会真正执行：
```redis
MULTI
SET account:1001:balance 1000
INCR account:1001:balance
GET account:1001:balance
EXEC
```
在 `MULTI` 和 `EXEC` 之间执行的命令不会立即返回最终结果，而是先返回 `QUEUED`。执行 `EXEC` 后，Redis 会按照命令加入的顺序依次执行；使用 `DISCARD` 可以取消还没有执行的事务。

需要注意，Redis 事务不等同于 MySQL 事务：命令一旦开始执行，通常不会因为其中一个命令失败而自动回滚。因此，使用事务时需要提前保证命令和参数正确。

Redis 还支持使用 `WATCH` 实现乐观锁。例如先监视一个库存 Key：
```redis
WATCH product:1001:stock
GET product:1001:stock
```
如果其他客户端在当前事务执行前修改了这个 Key，事务可能执行失败。这样可以避免多个客户端同时修改同一个数据时产生覆盖问题。
Pipeline 的作用是一次向 Redis 发送多个命令，减少客户端和 Redis 之间的网络往返次数。它主要解决网络效率问题，而不是事务问题。

Pipeline 可以减少网络通信次数，但其中的命令不一定具备原子性；如果需要保证多个命令作为一个整体执行，应使用事务或 Lua 脚本。Lua 脚本可以将多个 Redis 命令放在一个脚本中执行，并且脚本执行期间不会被其他 Redis 命令插入。
```redis
SET product:1001:stock 10
EVAL "local stock = tonumber(redis.call('GET', KEYS[1])); if stock and stock > 0 then return redis.call('DECR', KEYS[1]); else return -1 end" 1 product:1001:stock
```
这个脚本表示：只有库存大于 0 时才扣减库存；库存不足时返回 `-1`。
Lua 脚本适合处理判断并修改这类必须连续完成的操作，例如库存扣减、限流、优惠券领取和分布式锁续期。相比先执行 GET 再执行 DECR，Lua 可以避免多个客户端之间的并发问题。

#### Redis 数据可靠性与缓存
Redis 的数据主要保存在内存中，读写速度快；但服务重启或服务器故障可能导致数据丢失。因此 Redis 提供了持久化机制，将内存中的数据保存到磁盘。

##### RDB 与 AOF

**RDB** 是 Redis 默认支持的一种持久化方式：在某个时间点生成当前数据集的快照，保存为 RDB 文件。

- `SAVE`：直接在主进程中生成快照，执行期间可能阻塞其他请求，因此一般不建议在生产环境频繁使用。
- `BGSAVE`：创建后台任务生成 RDB 文件，Redis 主线程仍可继续处理客户端请求，更适合实际运行中的服务。

RDB 文件较紧凑、恢复速度较快，适合备份和快速重启；但它保存的是某个时间点的快照。如果两次快照之间 Redis 发生故障，最近一段时间的数据可能丢失。

**AOF** 则会记录 Redis 执行过的写命令。Redis 重启时，可以重新执行 AOF 文件中的命令来恢复数据。它通常比 RDB 更能减少数据丢失，但文件可能更大，恢复时也需要重新执行命令。

AOF 支持不同的刷盘策略，常见策略是每秒刷盘一次，在性能和数据安全之间取得平衡。实际使用中，RDB 更适合快照备份，AOF 更适合减少数据丢失，两者可以同时启用。

##### 过期、淘汰与缓存穿透

除了持久化，Redis 还会通过过期时间管理缓存数据。例如：
```redis
SET product:1001 "A" EX 60
TTL product:1001
```
当 TTL 变为 0 后，Key 会被 Redis 删除。Redis 的过期删除并不一定在时间刚到时立即删除，而是结合被动删除和定期检查机制完成。当客户端访问一个已经过期的 Key 时，Redis 会发现它过期并将其删除；同时 Redis 也会定期检查部分设置了过期时间的 Key。
如果 Redis 内存达到上限，还需要通过淘汰策略删除部分 Key。可以查看当前最大内存和淘汰策略：
```redis
CONFIG GET maxmemory
CONFIG GET maxmemory-policy
```
常见淘汰策略包括按照最近最少使用淘汰、按照访问频率淘汰、随机淘汰，以及只淘汰设置了过期时间的 Key。实际项目中，如果 Redis 主要用于缓存，通常会设置最大内存和合理的淘汰策略，避免 Redis 因内存不足无法继续写入。
缓存穿透是指请求查询一个 Redis 和数据库中都不存在的数据。由于缓存中没有数据，每次请求都会访问数据库，大量无效请求可能造成数据库压力。常见解决办法是缓存空值：
```redis
SET product:1 "__NULL__" EX 60
```
下次再查询 product:1 时，如果读取到 __NULL__，就可以直接判断数据不存在，而不必再次查询数据库。

#### 缓存击穿、缓存雪崩、主从复制与哨兵模式
缓存击穿和缓存雪崩，都是缓存失效后大量请求直接访问数据库、从而造成压力的问题。

##### 缓存击穿：一个热点 Key 同时失效

缓存击穿是指某一个访问量非常高的热点 Key 在过期瞬间，大量请求同时发现缓存不存在，然后同时查询数据库并重新写入缓存。例如某个热门商品的缓存即将过期，很多用户同时访问这个商品，所有请求都会执行以下流程：
```
查询 Redis，发现缓存不存在
        ↓
大量请求同时查询 MySQL
        ↓
大量请求同时重新写入 Redis
```
这种问题的特点是只有一个或少数几个热点 Key 失效，但访问量非常大。解决缓存击穿的常见方式是使用互斥锁，只允许一个请求负责查询数据库和重建缓存，其他请求等待或暂时返回。可以使用 Redis 的 SET NX EX 实现简单的互斥锁。
除了互斥锁，还可以使用逻辑过期解决缓存击穿。逻辑过期是指缓存数据本身不立即删除，而是在数据中保存一个过期时间。请求发现数据逻辑上已经过期后，可以先返回旧数据，再由后台线程异步更新缓存，这样可以减少用户请求等待数据库的时间。
##### 缓存雪崩：大量 Key 集中失效

缓存雪崩是指大量缓存 Key 在同一时间集中失效，导致大量请求同时访问数据库。例如系统在同一时间缓存了大量商品，并且都设置了 300 秒过期：
```redis
SET product:1001 "data-1" EX 300
SET product:1002 "data-2" EX 300
SET product:1003 "data-3" EX 300
```
如果这些 Key 的创建时间接近，那么它们也可能在接近的时间一起失效，造成数据库瞬间出现大量请求。缓存雪崩通常比缓存击穿影响范围更大，因为它可能涉及大量 Key。解决缓存雪崩的常见方式是给过期时间增加随机值，例如基础过期时间为 300 秒，再随机增加 0 到 60 秒。

##### 主从复制与 Sentinel

Redis 主从复制是指将一个 Redis 实例配置为主节点，将其他 Redis 实例配置为副本节点。主节点负责处理写请求，副本节点从主节点同步数据，也可以承担部分读请求。

副本节点可以通过 `REPLICAOF` 连接到主节点。主从复制能提供数据副本、分担读取压力，并在主节点故障时为故障转移提供候选节点。

需要注意，Redis 主从复制默认是异步复制：主节点成功执行写入后，副本节点可能还没有完全同步，因此主节点故障时仍可能丢失少量数据。主从复制本身不会自动选举新的主节点，也不会自动修改客户端连接地址；高可用和自动故障转移需要额外使用 Sentinel（哨兵）。

哨兵模式，也就是 Redis Sentinel，是建立在主从复制之上的高可用方案，主要负责监控、通知、自动故障转移和服务发现。一个典型的哨兵架构如下：
```
        Sentinel 1
       /          \
Sentinel 2      Sentinel 3
       \          /
        Redis 主节点
        /        \
   副本节点1   副本节点2
```
哨兵会持续检查主节点和副本节点是否正常。如果主节点发生故障，多个哨兵会共同判断主节点是否真的不可用，然后选出一个副本节点提升为新的主节点，并让其他副本节点重新复制新的主节点。应用程序通过哨兵查询当前主节点地址，而不是把主节点地址永久写死。
