## 7/13-7/19 工作与学习记录

## 一、项目工作

### 1. 坤元智算官网门户网站运维

本周继续对坤元智算官网门户网站进行日常运维和内容维护，重点处理了网站运行过程中的基础支持工作，并新增了算力通链接。

新增链接之后，用户可以从门户网站更方便地进入算力通相关服务，整体访问路径更加连贯。这个工作虽然看起来只是增加一个入口，但仍然需要考虑链接位置、页面展示、跳转是否正常，以及上线后是否会影响原有页面结构和用户使用习惯。


### 2. Chatbot 项目开发

本周主要投入在 Chatbot 项目的开发和整体架构理解上。这个项目并不是一个简单的聊天页面，而是一个可以根据用户需求生成、修改、构建并发布网站的 AI 应用平台。

项目的大致流程是：

```text
用户输入自然语言需求
        ↓
前端工作台发送 API 请求
        ↓
Rust 后端接收并整理项目上下文
        ↓
调用 AI 模型生成代码修改
        ↓
后端校验并直接应用修改
        ↓
构建生成的网站
        ↓
发布到对应的子域名
```

#### 前端：Next.js + React

项目的管理工作台使用 Next.js 和 React 实现，主要负责提供用户操作界面，例如：

- 展示项目列表和项目详情；
- 输入自然语言需求；
- 查看 AI 返回的消息；
- 显示文件变更和待审阅内容；
- 接受或拒绝 AI 生成的修改；
- 查看构建状态和部署结果。

选择 Next.js 和 React，主要是因为 React 适合把页面拆分成多个可复用组件，而 Next.js 在 React 基础上提供了更完整的项目结构和工程能力。对于这种包含项目列表、聊天区域、文件变更区域和部署状态的工作台来说，组件化可以让不同区域相对独立，后续修改也更容易控制。

这个项目里还有一个需要区分的地方：Next.js 工作台和 AI 最终生成的网站不是同一个前端。

```text
Next.js + React
└── 管理后台，用来创建和管理网站

React/Vite 项目
└── AI 实际生成并发布的网站
```

这样拆分的好处是，管理平台和生成出来的产品互不干扰。工作台负责“生产”，生成的网站才是最终交付给用户访问的“产品”。

#### 后端：Rust + Axum

项目后端使用 Rust，并通过 Axum 提供 HTTP API。Rust 后端不是用来直接绘制页面的，而是负责整个系统的业务编排：

- 接收前端请求；
- 管理项目和会话；
- 保存用户消息；
- 调用 AI 模型；
- 解析 AI 返回的文件修改；
- 执行项目构建；
- 检查构建结果；
- 发布网站并返回访问地址。

选择 Rust，主要是因为这个项目后端承担了比较多的控制职责，需要处理文件、构建命令、项目版本和发布流程。Rust 的类型系统和错误处理机制可以帮助提前发现一些问题，也能让文件路径、请求数据和业务状态更加明确。对于一个需要执行构建、处理多个服务并且不能轻易破坏旧版本的后端来说，Rust 更适合用来编写这种偏“系统编排器”的部分。

Axum 则负责把 HTTP 路由和 Rust 函数连接起来。例如前端发送消息时，请求类似：

```rust
// 路由示意
.route(
    "/conversations/{conversation_id}/messages",
    post(send_message_real),
)
```

它表达的意思是：当收到某个会话的 POST 消息请求时，就交给 `send_message_real` 函数处理。

后端函数可以从请求中同时拿到共享状态、路径参数和 JSON 数据：

```rust
async fn send_message_real(
    State(state): State<AppState>,
    Path(conversation_id): Path<String>,
    Json(request): Json<MessageRequest>,
) -> Response {
    // 查找会话、保存消息、调用模型并返回结果
}
```

这让我更清楚地理解了 API 的作用：API 不是一个抽象名词，而是把前端的操作转换成后端可以执行的函数调用。

#### 前后端通信：HTTP API 与 JSON

前端通过 `fetch` 调用后端 API。例如部署项目时，前端会发送：

```javascript
const response = await fetch(
  `/api/v1/projects/${encodeURIComponent(projectId)}/deploy`,
  { method: 'POST' }
);

const payload = await response.json();
```

这段代码的流程是：

```text
用户点击部署按钮
        ↓
JavaScript 发起 POST 请求
        ↓
Rust API 接收请求
        ↓
后端执行构建和部署
        ↓
返回 JSON 结果
        ↓
前端更新页面或打开网站地址
```

发送聊天消息时，请求体也是 JSON：

```javascript
await fetch(`/api/v1/conversations/${conversationId}/messages`, {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json'
  },
  body: JSON.stringify({
    content: text,
    attachments: []
  })
});
```

选择 JSON，是因为它结构清晰，前端 JavaScript 和 Rust 后端都容易处理，也适合表达消息、项目、文件变更等结构化数据。

#### SSE 流式消息

Chatbot 没有等模型全部生成完之后才一次性返回，而是使用流式方式把结果逐步发送给前端。这样用户可以看到类似“正在打字”的效果，等待感会更低。

后端产生的事件可以简单理解为：

```text
token
    AI 新生成了一小段文字

file_change
    AI 生成了文件修改建议

message_end
    当前回复结束
```

前端会不断读取后端传来的数据：

```javascript
while (true) {
  const { value, done } = await reader.read();

  if (done) break;

  buffer += decoder.decode(value, { stream: true });

  // 拆分事件并逐步更新页面
}
```

选择 SSE，是因为这个场景主要是服务器持续向浏览器推送生成进度，通信方向比较明确，不需要像 WebSocket 那样保持复杂的双向实时通信。对于 AI 回复、构建进度和部署状态这类服务端事件，SSE 结构更直观，也更容易在浏览器端使用。

#### AI 修改与直接部署机制

项目没有让 AI 直接执行 Shell 命令，也没有让 AI 无限制地操作服务器。AI 返回文件修改内容后，由后端负责解析、校验并直接应用到项目，然后进入构建和部署流程。

```text
AI 生成文件修改
        ↓
平台检查路径和格式
        ↓
后端直接应用修改
        ↓
执行项目构建
        ↓
构建成功后部署
```

这样设计是因为 AI 的输出不能直接当作可信操作。AI 负责生成代码，平台负责限制文件范围、校验格式并执行构建；只有构建成功后才会部署，从而避免错误代码直接进入线上环境。

#### Agent 工作流

这个 Chatbot 项目更像一个带执行能力的 Agent，而不是单纯的问答机器人。它的核心是一个“观察、决策、执行、验证”的循环：

```text
用户提出需求
        ↓
Agent 分析当前项目和用户意图
        ↓
调用 AI 生成文件修改
        ↓
后端解析并应用修改
        ↓
执行 npm ci / npm run build
        ↓
构建成功？
   ┌────┴────┐
   是       否
   ↓        ↓
部署上线   读取构建错误
            ↓
       反馈给 AI 修复
            ↓
        再次构建
```

Agent 的每一步职责并不完全相同：

- **观察**：读取用户需求、当前项目文件、构建日志和运行状态；
- **决策**：根据上下文判断需要创建或修改哪些文件；
- **执行**：写入文件、运行依赖安装和构建命令；
- **验证**：检查构建是否成功、产物是否完整，以及根目录是否存在 `index.html`；
- **修复**：如果构建失败，就提取有限的错误信息交给 AI，让它生成下一轮修复内容。

自动修复不是无限循环，而是有次数限制。这样可以避免某个错误让 Agent 一直重复构建，也能在多次修复仍然失败时保留问题现场，方便继续排查。

这条工作流和普通 Chatbot 的区别在于，普通 Chatbot 通常只返回文字：

```text
用户提问 → AI 返回答案
```

而这个项目会继续执行后续动作：

```text
用户提出需求
  → AI 生成修改
  → 系统执行修改
  → 构建验证
  → 失败后自动修复
  → 成功后直接部署
```

因此，AI 只是 Agent 中负责理解和生成方案的一部分，真正让它成为 Agent 的，是后端把模型输出接入了文件操作、构建、错误反馈和部署流程。

#### SQLite 与文件系统

项目数据分成两类保存：

```text
SQLite
└── 项目、会话、消息、变更等结构化信息

文件系统
└── 项目文件、生成文件、构建产物和发布版本
```

SQLite 适合保存有明确字段、需要查询和关联的数据；项目源文件和构建产物则更适合直接以文件形式保存。这样可以避免把大量代码内容全部塞进数据库，也让构建流程更自然，因为构建工具本来就是读取文件目录。

#### Vite 构建与发布前验证

AI 生成或修改文件后，后端会在项目目录中执行构建，例如：

```powershell
npm ci
npm run build
```

只有构建成功，并且产物中存在根目录 `index.html`，才允许进入发布流程：

```text
构建新版本
        ↓
检查 dist/index.html
        ↓
检查通过后替换当前版本
```

这样可以避免构建失败后把线上网站替换成半成品。Vite 适合这里的原因是它构建速度快、配置相对简单，并且适合生成独立的前端静态产物。

#### Caddy 反向代理

项目当前使用 Caddy 作为统一入口，第一版曾经考虑过 Nginx，后来改成 Caddy 主要是为了让本地开发入口和线上部署结构更接近，同时减少反向代理配置。

```text
浏览器
  ↓
Caddy :80
  ├── /api/*       → Rust API :4173
  ├── 其他路径     → Next.js :3000
  └── 子域名       → 已发布的网站
```

Caddy 不负责业务逻辑，它更像一个门卫：根据路径和域名把请求转发给正确的服务。这样浏览器只需要访问一个入口，不必直接区分前端 `3000` 端口和后端 `4173` 端口，也能减少跨域和本地/线上访问方式不一致的问题。

选择 Caddy 而不是继续使用 Nginx，主要是因为当前项目属于中小型 MVP，Caddy 配置更简洁，并且后续配置 HTTPS 更方便。Nginx 仍然是成熟稳定的方案，只是当前项目的路由场景用 Caddy 就已经足够。

#### Docker Compose

Docker Compose 用来描述整套服务如何启动和连接：

```text
api
  └── Rust 后端

web
  └── Next.js 工作台

caddy
  └── 统一入口
```

选择 Compose，是因为前端和后端运行环境不同，分别管理更清晰；同时又可以用一个配置文件启动整套系统，让本地环境和部署环境尽可能一致。

## 二、本周感想

这周最大的收获，是开始真正理解前端和后端是如何连通的。以前看到前端页面、API、后端服务和反向代理时，容易把它们当成一堆分散的技术名词；这周通过 Chatbot 项目的真实代码，把它们串成了一条完整链路：

```text
用户点击按钮
        ↓
前端 JavaScript 触发事件
        ↓
fetch 调用 API
        ↓
Caddy 根据路径进行反向路由
        ↓
Rust/Axum 路由接收请求
        ↓
后端执行业务逻辑并直接部署
        ↓
JSON 或 SSE 返回结果
        ↓
前端更新页面
```

我也开始理解反向代理存在的意义。它不是“又多加了一个服务”，而是把公网入口和内部服务隔离开：外部只需要访问一个地址，Caddy 再根据 `/api`、域名或其他路径，把请求交给对应的服务。

API 也不只是“前后端之间的接口”这么抽象。它实际上定义了双方约定好的通信方式：请求使用什么方法、访问什么路径、发送什么 JSON、后端返回什么数据，以及失败时如何表示错误。只要这个约定一致，前端和后端就可以分别开发。

这周还让我意识到，一个完整项目的重点不只是把功能写出来，还要考虑：

- AI 生成错误时怎么处理；
- 用户是否需要审阅修改；
- 构建失败时是否保留旧版本；
- 前后端服务如何统一访问；
- 数据应该存到数据库还是文件；
- 每个模块应该承担什么职责。

虽然目前还不能独立写完整个项目，但我已经开始能从“请求如何流动、模块如何分工、失败如何处理”的角度去理解项目，而不是只盯着某一行代码。

## 三、Rust 学习进度

本周 Rust 学习进度完成了《The Rust Programming Language》的第 11 章到第 14 章：

### 第 11 章：自动化测试

学习了如何使用 `#[test]`、`assert!`、`assert_eq!` 和 `assert_ne!` 编写测试，也了解了 `#[should_panic]` 和返回 `Result` 的测试写法。

```rust
fn multiply(a: i32, b: i32) -> i32 {
    a * b
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_multiply() {
        assert_eq!(multiply(4, 5), 20);
    }
}
```

通过这一章，我开始理解测试不是额外的负担，而是让程序自动检查行为是否符合预期。

### 第 12 章：构建命令行程序

完成了 `minigrep` 项目的学习，串联了命令行参数、文件读取、字符串搜索、`Result` 错误处理、生命周期和测试。

```rust
fn search<'a>(query: &str, contents: &'a str) -> Vec<&'a str> {
    let mut results = Vec::new();

    for line in contents.lines() {
        if line.contains(query) {
            results.push(line);
        }
    }

    results
}
```


### 第 13 章：闭包与迭代器

学习了闭包、`iter`、`into_iter`、`map`、`filter`、`collect`、`sum`、`any` 和 `all`。这些方法可以把集合处理流程写得更加清晰。

```rust
let result: Vec<i32> = numbers
    .into_iter()
    .filter(|number| number % 2 == 0)
    .map(|number| number * 10)
    .collect();
```

这段代码可以理解为：取出数字，筛选偶数，把偶数乘以 10，最后收集成新的 `Vec`。

### 第 14 章：Cargo 与 Crates.io

了解了 `Cargo.toml`、`Cargo.lock`、依赖管理以及常用命令：

```powershell
cargo check
cargo build
cargo run
cargo test
cargo fmt
cargo clippy
```

这一章让我对 Rust 项目的工程化结构有了更完整的认识。Cargo 不只是运行代码的工具，也负责项目创建、依赖管理、编译、测试和格式化。
