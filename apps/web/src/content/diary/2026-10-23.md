## 10/19–10/23 工作记录

这周主要还是在智问和视算这两个项目上。视算继续改工作室里的问题，文件夹、素材卡片、画布这些地方又调整了一轮，也改了媒体文件的访问方式。智问这边则在整理聊天功能、账号、数据库和部署，还有后端调用模型的接口。

这周做下来，感觉自己还是有以前的问题，需求听到了，但没有完全理解就开始往下做。尤其是两个平台互通这件事，被指出来以后再回头看，确实绕了不少没必要的东西。代码写出来了，实际让别人用的时候却多了门槛，这部分后面得重新改。

## 一、坤元智问

### 1. 聊天功能和账号

智问这边先重新整理了项目要保留的内容。相当于整个项目的重构，之前 chatbot 里还有建站、生成代码这些东西，现在先集中做聊天，包括邀请码注册、登录、多轮对话和历史记录。用户登录以后，看到的是自己的会话，不能几个账号共用一份聊天记录，做了用户隔离。

这周智问已经提交的内容主要是管理员账号和生产部署准备的设计文档，其他本地改动还在继续整理。

### 2. 数据库和部署准备

数据库这边整理了 PostgreSQL 的存储和迁移方案。本地有现成的数据和配置，开发的时候容易忽略初始化这一步，到了新环境就不一样了。账号、会话、消息这些表怎么建立，服务启动前数据库是否就绪，都得考虑进去。

部署准备使用 Docker Compose，把聊天服务和 PostgreSQL 放在各自对应的容器里，不去混用其他项目的数据。备份和回滚的操作也整理进了文档，不过服务器上的实际部署和恢复还需要继续验证。

智问准备放在官网的 `/zhiwen` 路径下面，本地开发时则是直接从根路径访问。

### 3. 前端和模型接口

前端在往 React + Vite 调整，路由用 React Router。本地已经有相关文件和配置的改动，还检查登录、注册、会话切换、消息显示，以及 Markdown 和公式这些功能。尤其是改框架以后，不能只看页面样式没变就觉得已经好了。

另外就是后端调用模型的接口。这里一开始想偏了，看到视算有 API Key 和额度管理，就把类似的东西也放进了智问的调用方式里。但是这次的需求是让两个平台的能力互通，另一个后端可以通过地址调用模型，不是让开发人员再去开通一套服务、申请额度。

接口格式也被单独指出来了。对方给了一个标准的聊天调用示例，里面就是调用地址、`model` 和 `messages` 这些内容。我之前给出去的接口，应该先和这个示例逐项比较，看看路径、参数和返回到底有什么区别，而不是只觉得自己这里已经能请求、能返回就可以了。

目前本地接口和配置还需要按这个要求继续核对，实际调用方能不能直接接上，也要通过联调确认。

## 二、坤元视算

### 1. 视频卡片拖入裁剪时间轴

视算这周先处理了视频卡片拖不进裁剪时间轴的问题。生成的视频卡片、保存下来的素材卡片，以及文件夹里的视频，都涉及拖拽，不能只改其中一种。

卡片本身还带着播放、下载和其他操作，拖拽和点击也会互相影响。所以这次除了卡片，也一起调整了文件夹列表项和相关样式。

### 2. 文件夹和画布的位置

文件夹卡片这周又改了一轮，包括宫格展示时的高度，以及画布缩放后卡片尺寸的计算。文件夹里面的视频多起来以后，内容区需要能滚动，不能一直往下撑；卡片尺寸变化以后，外层的高度也得跟着改动。

画布上的位置也重新处理了。用户可能已经把画布拖到别处，或者放大、缩小了，这时候新建文件夹和新任务不能还按最开始的位置往里放，否则东西虽然创建了，人却看不到。现在按当前看到的画布范围计算放置位置，并考虑已有卡片占用的位置。

新任务出现后的定位也做了调整，让用户更容易找到刚生成的内容。画布里东西少的时候，这个问题不明显，素材一多，再加上拖动和缩放，就容易分不清刚才的任务跑到哪里去了。

### 3. 隐藏状态和刷新恢复

画布卡片的隐藏状态补了保存。用户已经从画布上隐藏的内容，刷新以后不应该又全部出现。这部分增加了服务端记录和对应接口，不只是页面上临时把卡片藏起来。

本地保存的布局、隐藏状态、文件夹折叠和显示方式，也按工作空间区分了存储位置。之前这类状态如果混在一起，切换工作空间时就可能带出不属于当前空间的显示记录。

这些修改都和画布状态有关，后续还得连着看。比如隐藏后刷新、新建任务后移动画布、切换工作空间再回来，光看刚改完时页面正常还不够。

### 4. 媒体文件改由 Nginx 提供

媒体访问这边调整为由后端先检查访问权限，再交给 Nginx 发送实际文件。这样视频文件不用一直由业务接口读取和返回，但用户是否有权限访问，仍然由后端判断。

对应的媒体目录挂载、Nginx 内部路径和前端资源地址也一起改了。这次改的是媒体文件怎么送到浏览器，具体加载效果还要看部署后的表现。


## 三、这周被指出来的问题

这周主要的问题，还是看东西太表面。看到之前的项目有一套做法，就觉得自己也可以照着做，至于为什么这样做、和我现在的需求是不是一样，没有继续往下想。

API Key 和额度这件事就是很具体的例子。视算有面向用户的套餐和计费，智问这次要解决的是平台之间的调用。我当时把注意力放在怎么补齐接口管理上，却没想调用的人为什么要经过这些步骤。最后反而让原本可以直接接的东西变复杂了，也难怪会被问，开发自己用为什么还要一个额度。

后面再遇到类似需求，还是得先把实际过程写下来。比如这次就是哪个后端发请求、智问收到什么、再去调哪个模型、结果怎么返回。把这些说清楚以后，再看中间到底缺什么。不能先拿一套现成的功能往上套，套完了才发现用不上。

标准接口的问题，我也需要补课。主要也是第一次写这个，很多标准不是很了解，后续应该补齐一下这方面的知识。别人已有的程序按标准发过来以后能不能用，这些都要自己弄明白。

还有一句话我觉得说的很有道理，代码写出来只有自己能用，那还不叫工程。现在回头看，自己开发时确实有不少默认条件：配置是自己填的，启动顺序自己知道，数据库和环境也早就准备好了。换一台机器、换一个人，可能第一步就卡住。不能把这些都留给接手的人去猜。

以后交出去的东西，至少接口示例得能直接照着调用，启动和部署说明得能跟着做。有些配置是只有自己知道的，就得写下来；有些步骤还没验证，就说明还没验证。别人拿到以后还需要我在旁边一直解释，说明这一部分还没做完。

AI 这边也一样。它给出来的方案往往很完整，账号、鉴权、额度、限流都可以一口气写出来，但我不能因为它写得全就觉得合理。这周的问题就是前面判断没有做好，后面又顺着现成方案继续做。需求理解这一步省掉了，最后还是得花时间返工，而且代码越多，改起来越麻烦。
