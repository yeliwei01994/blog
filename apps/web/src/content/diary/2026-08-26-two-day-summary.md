### 这两天主要做了什么

这两天同时推进了两个项目，但工作的内容不一样：坤元门户网站主要集中在页面结构、导航关系和视觉细节；个人视觉分析平台主要集中在视频任务链路、YOLO 检测回放、规则判断、事件审核和性能优化。

坤元门户网站的工作偏前端页面完善，重点是把生态合作页面和首页细节调整得更清楚、更稳定。视觉分析平台的工作则更偏完整链路验证，从视频上传、Redis 任务队列、Worker 抽帧、YOLO 推理，到事件入库、证据展示和视频回放，逐步把原本分散的功能串起来。

其中页面组件负责内容和视觉结构，路由文件负责页面能否被访问，导航组件负责入口展示，验证脚本则把页面要求固定下来。这样修改页面时，不只是看浏览器效果，也能检查页面是否仍然满足约定。

### 2. 首页导航调整

首页导航中移除了“软件产品”入口，但软件产品页面和路由仍然保留，因此这次调整只是改变用户从首页进入页面的方式，并没有删除原有页面能力。

同时保留了“生态合作”入口，并通过页面验证、TypeScript 和 ESLint 检查确认路由关系没有被破坏。

### 3. 导航滚动白线问题

首页导航滚动到不同颜色区域时，底部出现了一条比较明显的白线，影响导航和下方内容之间的衔接。

排查后确认，问题主要不是布局高度，而是滚动态导航的实体底部边框和半透明背景叠加后产生了过强的边缘对比。最后采用的修改方式是：

```text
移除 border-b
保留 backdrop-blur-md
使用更明确的 bg-white/30
保留柔和阴影
```


### 4. 首页算力资源卡片

首页算力资源区域原本存在几个问题：普通资源卡片之间的层级不够明显，边框和分隔线颜色接近，小字号文字对比度偏低，不同计费方式放在一起时不容易横向比较，CTA 卡片和普通资源卡片的角色差异也不够突出。

这次主要调整了视觉表达，没有修改价格数据和核心交互逻辑：

- 普通卡片增加渐变背景和更清晰的边框；
- 增加 hover 上浮和阴影效果；
- GPU 标签保持右对齐；
- 提升价格、参数说明和底部分隔线的可读性；
- CTA 卡使用更明显的蓝色渐变、发光边框和阴影；
- CTA 按钮改为更清晰的实心主按钮，并增强 hover 反馈。

这部分的重点不是增加更多装饰，而是让用户更容易区分普通资源、价格信息和主要行动入口。视觉层级清楚以后，页面不需要依赖大量文字解释，用户也能理解不同卡片的作用。



## 二、个人视觉分析平台

### 1. 从视频上传到事件审核的完整链路

这两天对视觉分析平台的主要升级，是把系统从“上传视频并调用模型”推进到一条可以验证的视频事件分析闭环，加上修复一些bug和测试功能：

```text
上传视频
    ↓
Redis vision:jobs
    ↓
Worker 抽帧
    ↓
YOLO 推理
    ↓
规则引擎
    ↓
事件和证据入库
    ↓
事件流与详情审核
    ↓
原始视频或 YOLO 检测回放
```

MySQL 负责保存任务、事件、规则和审核历史；Redis 负责异步任务消息；视频和图片目前保存在本地 `media` 目录。这样的划分让视频文件、长期业务数据和临时任务消息各自承担不同职责。

### 2. 视频任务与 Worker

平台现在支持视频上传、任务创建、状态更新和本地媒体保存。Worker 在 `WORKER_MODE=1` 时从 Redis Stream `vision:jobs` 消费任务，并使用 FFmpeg 对本地视频抽帧，再将视频帧交给 YOLO 服务处理。

任务状态、处理进度和源文件路径会持久化到 MySQL。上传文件名会先进行安全清理，避免文件名中包含路径穿越内容。任务也支持重命名、删除和软删除，删除时需要区分数据库记录、原始视频和检测回放，不能因为删除一条任务而误删其他任务的媒体文件。

Worker 调用 YOLO 服务的单帧接口时，需要把检测类别、置信度、边界框、时间戳和模型版本转换成平台内部使用的数据结构。边界框还要兼容像素坐标和 0～1 的归一化坐标，否则会出现检测框位置偏移的问题。

### 3. 事件证据和规则配置

事件详情已经从占位图片改为真实抽帧证据。证据帧保存到：

```text
media/evidence/<event-id>/
```

证据帧包含时间点、检测框和目标信息，前端可以在事件详情中查看对应画面。页面还增加了中文检测摘要，例如“人员 11 次检测 · 平均置信度 34%”，并将内部事件类型转换成更容易理解的文字：

```text
person_stay        → 人员停留
person_enter_zone  → 人员进入区域
person_count_limit → 最大人员数量
```

规则方面增加了人员停留、人员进入区域和最大人员数量规则，支持最低置信度、最短持续时间、人数上限和启用状态。区域编辑支持鼠标拖动绘制矩形和多边形，也支持空白画布和视频证据作为绘制背景。

之前出现过一个问题：重置区域后点击“应用区域”没有效果。修复后，规则保存和区域应用能够按照新的配置执行。Worker 开始任务前还会从 MySQL 刷新规则，保证保存后的规则能够应用到新任务，而不是继续使用旧的内存配置。

另外，区域外目标仍触发事件的问题也已经修复。鼠标移动绘制增加了节流，避免拖动区域时前端频繁更新导致卡顿或黑屏。

### 4. 事件审核和查询

事件状态扩展为：

```text
待复核 → 确认 / 忽略 → 已处置 → 已关闭
             └──────→ 处理中
```

审核操作支持审核人、备注和处置结果，并保存旧状态、新状态、审核时间和审核历史。详情页可以展示审核时间线，审核按钮增加处理中状态、成功提示、失败提示和重复提交保护。

事件查询还增加了组合查询、分页、排序、CSV 导出和 HTML 报告接口。这样事件不仅能被检测出来，也能够被筛选、确认、追踪和导出，逐渐从单纯的模型结果变成可操作的业务记录。

## 三、视觉平台的性能优化

### 1. 减少前端状态轮询

浏览器中大量重复出现的 `GET` 请求主要来自任务状态轮询，而不是重复上传。原来的轮询固定每 1 秒请求一次，视频处理时间越长，请求数量越多。

这次改成退避轮询：

```text
1 秒 → 2 秒 → 3 秒 → 4 秒 → 5 秒
```

任务状态发生变化时重新使用较短间隔；任务长时间没有变化时逐步降低请求频率。这样可以减少 API 和浏览器端的压力，同时不影响任务最终状态的获取。

事件列表接口增加 `limit` 参数，默认最多返回 50 条，前端显式请求有限数量的数据，避免事件数量增长后一次返回过多内容。

### 2. 上传过程改为流式写入

视频上传不再一次性读取到内存，而是按数据块写入临时文件，上传完成后再进行最终文件切换：

```text
接收上传数据
    ↓
写入临时文件
    ↓
上传完成并校验
    ↓
切换为最终文件
```

这样可以降低大视频上传时的内存峰值。上传失败时也可以清理临时文件，不会留下一个看起来完整、实际内容不完整的视频文件。

### 3. 降低默认检测频率

视频检测间隔从 100ms 调整为 200ms，并支持通过环境变量配置：

```text
DETECTION_INTERVAL_MS=200
```

有效范围为 100ms 至 5000ms。对于非实时分析场景，降低抽帧和推理频率可以减少 CPU、GPU、磁盘和 YOLO 服务压力。这个参数不能盲目调大，因为间隔过大可能会漏掉持续时间很短的事件，后续需要结合真实视频验证准确率。

### 4. YOLO 批量推理

新增批量推理接口：

```http
POST /v1/infer/batch
```

一次请求上传多张帧图片，并携带每帧的 `frame_id` 和 `timestamp_ms`。当前默认每批处理 4 帧：

```text
YOLO_BATCH_SIZE=4
```

服务端将多张图片作为一个 batch 传给 Ultralytics YOLO，避免每一帧都单独建立 HTTP 请求和执行一次完整调用。

Worker 使用有上限的并发处理，默认最多同时执行 2 个批次：

```text
YOLO_CONCURRENCY=2
```

并发参数限制在 1 至 4 之间，批量大小限制在 1 至 16 之间，避免配置过大导致内存或显存压力失控。

批量响应不能简单依赖数组顺序，而是通过 `frame_id` 关联原始帧。即使不同批次返回顺序不同，也不会把检测结果写入错误的帧。Worker 收集并发结果后，会恢复处理顺序，同时保留每帧的时间戳、检测框和原始帧路径。

一个批量请求可以抽象成下面的形式：

```json
{
  "frames": [
    {
      "frame_id": "frame-001",
      "timestamp_ms": 0,
      "image": "..."
    },
    {
      "frame_id": "frame-002",
      "timestamp_ms": 200,
      "image": "..."
    }
  ]
}
```

其中 `timestamp_ms` 用来恢复视频时间轴，`frame_id` 用来保证结果关联正确，图片内容则交给 YOLO 服务完成批量推理。

## 四、YOLO 检测回放

### 1. 检测回放

视频任务增加检测回放地址、状态和错误信息字段。Worker 完成推理后生成带检测框的 MP4 回放，回放画面包含检测框、类别名称、置信度和时间戳。

详情页增加“原始视频”和“YOLO 检测回放”两个选项，默认播放原始视频，避免用户把带框回放误认为原视频。切换视频源后会重新创建或正确更新 `<video>` 元素，修复了切换后仍然复用旧视频源的问题。

删除任务时只清理对应的检测回放，不删除原始视频，避免不同用途的文件被混在一起处理。

### 2. 回放低帧率和时长错误

之前出现过两个明显问题：回放帧率偏低、帧数不足，以及原本 9 秒的视频生成后变成 24 秒。排查后确认，检测结果的数量不能代表原视频的时长，也不能直接用检测帧数量计算回放时长。

现在的处理逻辑是：

1. 使用 FFprobe 读取原视频真实时长、FPS 和总帧数；
2. YOLO 仍按可控抽帧间隔推理，避免推理成本过高；
3. 根据原视频总帧数复制或保持最近一次检测画面；
4. 按原视频 FPS 编码；
5. 回放时长优先使用原视频时长，不再使用检测结果条数计算。

批次大小和并发数只影响推理速度，不应改变视频时长或回放帧数。这次修复的关键是把“推理采样频率”和“最终视频时间轴”分开处理。



## 五、Claude Code 课程学习收获

这两天还补充学习了 DeepLearning.AI 与 Anthropic 的《Claude Code: A Highly Agentic Coding Assistant》课程。课程的重点不是让 AI 代替开发者写更多代码，而是说明如何把 AI 编程助手放进正常的软件工程流程中：先理解项目，再明确上下文，随后规划、实现、测试、调试、重构，最后通过 Git 和自动化工具保持修改可追踪。

### 1. 先理解代码库，再开始修改

课程反复强调，面对陌生项目时不要直接让 Agent 修改代码，而应该先了解项目结构、启动方式、依赖关系、数据流和现有约定。稳定的项目知识可以写入 `CLAUDE.md` 一类的项目说明文件，具体任务再通过文件名、目录和问题描述补充上下文。

这个方法也适用于这两天的实际工作。修改坤元门户网站时，需要先定位导航组件、路由配置和页面组件，不能只看到页面上的文字就直接修改。排查视觉分析平台的问题时，也需要沿着 API、Redis、Worker、YOLO 和视频编码的调用链逐段确认，不能只根据浏览器现象猜原因。

### 2. 先规划，再小步修改

课程建议复杂任务先拆分目标、相关文件、实现步骤和验证方式，再开始编码。修改过程中尽量保持范围明确，一次解决一个问题，避免同时改动过多模块后无法判断是哪一处引入了问题。

这两天的两个项目也采用了类似方式。门户网站先分别处理生态合作页面、导航入口、滚动白线和算力卡片；视觉分析平台则把任务队列、规则区域、事件审核、回放和批量推理分开处理。这样每次修改都有明确的目标，出现问题时也更容易回到对应的代码路径。

### 3. 用测试和运行结果反馈修改

课程中比较有价值的一点，是把测试、日志、浏览器截图和实际运行结果作为 Agent 的反馈，而不是只把错误信息交给 Agent 让它凭感觉修复。推荐的过程是：先复现问题，再定位调用链，必要时增加测试，修改后重新运行验证。

这也是本次回放问题能够解决的原因。9 秒视频生成成 24 秒时，不能只修改播放器显示，而是要检查 FFprobe 读取的原视频时长、抽帧数量、编码 FPS 和回放时长计算方式，最后确认检测结果数量不能直接代表视频时长。批量推理也需要通过 `frame_id` 和 `timestamp_ms` 验证结果没有写错帧，而不能只确认接口返回成功。

### 4. 项目记忆和自动化检查

课程还介绍了项目级说明文件、Git worktree、GitHub、Hooks、MCP 和自动化检查。它们解决的是不同问题：项目说明文件保存稳定知识，Worktree 隔离并行任务，Git 记录变更，Hooks 和 CI 自动执行检查，MCP 让开发助手可以使用设计稿、浏览器或其他外部工具。

课程中的具体命令和工具配置可能会随版本变化，不能直接当作当前操作手册使用；但“清晰上下文、先规划、小步修改、自动验证、保留可追踪记录”这套方法仍然适用。


## 六、总结

这两天在两个项目上完成的事情不同，但都不只是表面修改。坤元门户网站重点解决了页面入口、合作伙伴展示和首页视觉层级问题，并通过类型检查、ESLint、构建和页面验证确认修改结果。视觉分析平台则进一步打通了视频任务、Redis 队列、Worker 抽帧、YOLO 推理、规则判断、事件审核和检测回放，同时对轮询、上传、抽帧和批量推理进行了性能优化。

另外，通过 Claude Code 课程的学习，我对“如何使用 AI 协助开发”也有了更明确的认识。AI 更适合参与调查、规划、实现和验证，但前提是开发者提供清晰的项目上下文，并对修改结果负责。实际工作中仍然需要自己确认需求、判断根因、选择修改范围，并通过测试和运行结果确认是否解决了问题。
