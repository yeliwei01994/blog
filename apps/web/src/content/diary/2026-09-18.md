## 9/14–9/18 工作与学习记录

## 一、项目工作

### 1. 公司网络测算

这周做了一部分公司的网络测算，也算是重新干回了网络工程的老本行。

这次做测算时，也重新回顾了以前做网络工程时的思路：先梳理需求和现状，再按照实际使用情况去估算资源，而不是一上来就只看某个设备或者某个参数。虽然现在主要工作方向已经偏向开发，但网络这部分的基础知识还是很有用，后续无论是做部署、服务器、内网服务还是项目上线，都离不开这些底层的东西。

这周还专门针对 Codex 连接偶尔不稳定的问题做了一轮网络综合测试。平时使用时有时会感觉请求等待比较久，偶尔也会出现连接异常；但只靠体感很难判断，到底是本地 Wi-Fi、路由器、代理，还是外网链路的问题。所以这次把测试拆开做了：一边测本地网关的稳定性，一边连续发起 HTTPS 请求，同时也跑了几轮 Codex 的长会话保持测试。

结果看下来，本地这一段其实比较稳定：网关 Ping 了 300 次没有丢包，P50 延迟只有 2 ms，P95 是 9 ms。Codex 长会话连续跑了三轮，每轮大约 10 分钟，也没有复现持续断连。真正有波动的是外部 HTTPS 请求：虽然 600 次里成功了 598 次，但典型请求大概就要 1.12 秒，P95 会到 2.1～2.3 秒，最长的一次接近 6.6 秒，中间还抓到了两次异常样本。

这说明问题不太像是电脑到路由器这一段 LAN 一直不稳，更像是代理、外网出口或上游链路偶发的长尾抖动。不过现有路由器属于比较傻瓜的设备，只能满足基础联网，没法做策略路由、按设备或业务分流、出口切换、QoS 和持续的网络质量监控。即使已经大致判断问题偏向外部路径，现在也没有太多手段继续验证“换一个出口会不会改善”“Codex 和代理流量要不要单独走规则”。

所以后续还是希望公司能换一台可以做策略配置的企业级路由器吧，用这种傻瓜机后续要上设备咋办。不是说换完就一定能把 Codex 的连接问题完全解决，而是先把分流、监控和对比测试这些能力补上。这样下次再遇到不稳定，至少能知道问题在哪一段，也能有办法去调整。

### 2. 官网坤元智算小助手正式接入 API

官网上的坤元智算小助手这周完成了正式 API 接入。

之前页面上的小助手更多还是前端展示和交互层面的内容；正式接入 API 之后，用户输入的问题才能真正发送到后端，再拿到模型返回的结果。这里不只是把一个接口地址接上，还需要处理请求中的状态变化、加载过程、返回内容、异常情况，以及页面交互和接口结果之间能不能对得上。

目前小助手还只是一个雏形功能，所以这一轮先接入市面上的免费 API，重点是把完整链路跑通，同时看看不同平台实际使用下的效果和稳定性。

一开始尝试了 AMD 开发者平台和英伟达开发者平台提供的模型接口。它们本身有不少模型可以试用，但因为服务在海外，实际请求时延比较高，偶尔还会有明显卡顿。对于官网上的聊天小助手来说，用户发出问题后如果要等很久，体验就会比较差；即使模型本身能正常回复，放到真实页面里也不太合适。

最后接入了国内的硅基流动平台，模型选择了 **Qwen3-8B**。国内接口在当前网络环境下响应会更顺一些，至少先把“用户提问 → 后端请求模型 → 前端显示回复”这条链路稳定地跑起来。后面如果小助手的功能继续扩展，再根据实际访问量、回答质量、上下文能力和成本去考虑更换模型或增加不同模型的选择。

另外也提了一个后续方向：像 Qwen3-8B 这类小模型，其实可以考虑本地部署。官网小助手问到的内容，大部分还是围绕公司的产品、算力服务、案例、文档和常见问题，不一定每次都需要依赖一个很大的通用模型。后面如果把这些资料整理成企业知识库，再让模型根据检索到的内容来回答，针对性可能会更强。

这样做的好处不只是减少对外部 API 的依赖。对于“公司有哪些产品”“某个服务怎么使用”“价格或配置应该看哪里”这类问题，通用模型有时会回答得比较泛，甚至可能补出并不存在的信息；接上知识库之后，回答可以更多基于已有文档和实际资料来组织，内容会更贴近业务。模型本身不需要特别大，关键还是知识库是否完整、检索是否准确，以及回答时能不能把资料真正用起来。

当然这部分还只是一个建议，本地部署也会多出模型运行、显存资源、知识库更新和效果评估这些事情。现阶段先用 API 把功能和交互做出来是比较合适的，后面小助手的使用场景更明确之后，再考虑把本地小模型和企业知识库接进去。


```text
用户输入问题
    ↓
前端发送请求
    ↓
后端调用 API
    ↓
返回模型结果
    ↓
前端更新聊天内容和状态
```

正式接入之后，除了功能能不能跑通，也要继续看用户实际使用时的体验。例如请求过程中有没有明确反馈、接口失败时页面会不会卡住、回复内容过长时展示是否正常。

### 3. 坤元视算页面交互和视觉优化

这几天大部分时间都在做坤元视算的主页、文档和后台交互优化。

这部分工作表面上看是页面调整，但实际涉及主页的信息展示、文档的阅读路径、后台的操作反馈、页面之间的跳转节奏、动画出现的时机，以及不同模块之间的视觉统一。前面已经有了基础页面，这一轮更多是在补交互和细节，把原来“能用”的页面继续往“看起来更完整、操作更顺”去推进。

**本周前端工作**

- 重构官网首页视觉，统一浅雾蓝、深海军蓝和品牌蓝的视觉体系。
- 完善首页 Hero 视频、视频预览、价格区、代码示例和产品指南展示。
- 优化首页滚动入场动效、价格标签动画、导航状态及移动端布局。
- 优化首页 Hero 视频加载策略，包括首屏预加载、离屏暂停和减少动态效果处理。
- 优化移动端导航菜单，调整菜单位置、触控区域和展开布局。
- 更新登录注册页，新增光影创作室视频背景及对应静态封面。
- 完善登录注册页响应式布局，移动端隐藏视频媒体并减少资源请求。
- 增加官网及登录页相关素材、字体和视频资源。
- 优化文档中心导航、搜索、代码复制反馈及正文入场动画。
- 优化控制台侧栏、按钮反馈、复制提示和页面交互效果。
- 增加首页、登录页、文档页及导航交互相关测试。

**首页视觉、内容与性能**

首页这部分不只是换了一套颜色，而是重新梳理了整体视觉。现在主要围绕浅雾蓝、深海军蓝和品牌蓝来统一页面的主色，标题、卡片、按钮、背景和状态色之间尽量保持同一套逻辑。之前有些模块单独看没什么问题，但放在一个页面里会有点跳；这一轮把 Hero、价格区、代码示例和产品指南这些重点模块一起调整，更多是在处理它们之间的层级和节奏。

Hero 区域重点补了视频、视频预览和首屏加载策略。首页的视频不只是为了增加动态效果，还承担了第一眼的氛围和产品展示作用，所以需要考虑用户进来时先看到什么、视频什么时候开始加载、滚到别的区域后还要不要继续播放。现在增加了首屏预加载和离屏暂停，也减少了一些不必要的动态效果，尽量在视觉效果和加载体验之间找一个平衡。

滚动入场动画、价格标签动画和导航状态也都重新扣了一遍。动画做得太少会显得页面比较平，做得太多又容易打断阅读，所以还是更希望它们是跟着信息出现的：用户滚到对应模块时，内容自然地出现；需要强调的价格或按钮有一点反馈，但不会一直抢注意力。

**移动端与登录注册页**

移动端这次也单独做了不少调整。桌面端的导航、视频和卡片布局直接缩小到手机上通常不太好用，所以重新调整了导航菜单的位置、展开方式和触控区域，也把部分模块的间距和排列方式重新适配。重点不是简单做成“能显示”，而是让用户单手操作时不会太挤、菜单打开后信息也能看得清楚。

登录注册页也更新了一轮，新增了光影创作室的视频背景和对应静态封面。视频背景在桌面端能让页面氛围更完整，但在移动端继续加载视频的意义不大，还会增加资源消耗，所以移动端直接隐藏视频媒体，用静态内容保证页面能更快打开。这部分也补了响应式布局，避免不同屏幕下输入框、按钮和说明文字挤在一起。

**文档中心与控制台交互**

文档中心和主页的目标不一样。主页更偏介绍和引导，文档更需要让用户快速找到信息，所以这次主要优化了导航、搜索、代码复制反馈和正文入场动画。导航和搜索做得顺一点，用户找内容时就不用在页面里反复翻；复制代码后给一个清晰的提示，也比用户点完不知道有没有复制成功要好很多。

控制台这边则更偏操作体验，主要调整了侧栏、按钮反馈、复制提示和页面交互效果。后台不需要太多花哨的动画，但每一步操作都应该有反馈：按钮有没有点到、内容有没有复制、页面是不是正在切换、任务有没有开始处理。这些细节平时看起来不大，连续使用时会很影响整体感觉。

**视频素材、资源与测试**

这轮也做了不少动画和视频素材的尝试。视频主要使用 MiniMax 生成，过程中生成了很多版本，再从里面挑更合适的素材放到页面里。AI 生成视频给了很多选择，但也不是生成出来就能直接使用：画面节奏、主体位置、色调、时长都要能和页面布局配合；有时候一个视频本身效果不错，放到页面里却不合适，还是要重新换素材、调整裁切，或者重新考虑它出现的位置。

除此之外，也补充了官网和登录页相关的素材、字体和视频资源，并给首页、登录页、文档页及导航交互增加了一些测试。页面现在涉及的视频、动效和交互比之前多很多，不能只看“视觉上能不能展示”，还要确认导航展开、页面跳转、复制反馈和不同屏幕下的表现不会因为后续调整被弄坏。整体来说，这一轮除了继续扣视觉细节，也把加载、适配和稳定性一起往前推进了。
