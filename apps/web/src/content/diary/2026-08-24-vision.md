vision_jobs
| 字段 | 内容 |
|---|---|
| `id` | 自动生成的 UUID |
| `filename` | 视频文件名 |
| `duration_ms` | 视频时长，单位毫秒 |
| `status` | 初始通常为 `pending`，Worker 处理后变为 `completed` 或 `failed` |
| `progress` | 处理进度 |
| `source_uri` | 本地视频路径，例如 `media/test.mp4` |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |


events
id：事件 UUID
job_id：关联的视频任务
event_type：事件类型，例如 person_stay
start_time_ms、end_time_ms：事件时间范围
severity：严重等级
status：unreviewed、confirmed 或 ignored
confidence：置信度
objects_json：检测到的目标
evidence_json：证据信息
analysis_json：分析结果
rule_version：规则版本
prompt_version：提示词版本
detector_version：检测器版本

























前端上传视频
  ↓
API 立刻自己跑 ffmpeg + YOLO
  ↓
等几十秒或几分钟
  ↓
前端才能收到响应

有redis
前端上传视频
  ↓
API 保存文件和任务记录
  ↓
Redis 记一条“处理这个 job_id”
  ↓
API 立刻返回给前端
  ↓
Worker 空闲时从 Redis 取任务，慢慢分析

上传接口能快速返回；
多个视频会排队，不会同时把 API 压垮；
可以启动多个 Worker，一起消费不同任务；
API 重启不需要自己记住“哪些视频待处理”；
Worker 和 API 可以分开部署、分开扩容。
