## 9/1–9/4 周报

### 本周心得

这周是第一次比较完整的接手和推进一个项目，整体过程中收获了很多，也发现了自己在项目开发和细节的方向存在不少的不足。

这周主要参与了坤元视算的多项工作，周一首先对整个项目的结构目录进行了重构，随后接下来今天进行了前台门户网站的重建，文档页面的开发、控制台页面和导航头的优化、以及性能优化等。除了实现功能一起，还涉及了页面样式调整、各种小功能的实现、测试和问题修复。通过这一周的实践，我对一个项目从功能开发到页面体验，再到测试和维护的完整过程有了更深的认识。

第一次接手项目时，我对项目的整体结构、业务逻辑，和现有的工能还不理解还不够深入，有些时候并没有完全理解清楚原有的代码，就直接开始修改，导致后面出现了反复调整，样式冲突，功能bug等问题，有些修改看起来只是局部调整，但实际上会影响到公共组件、导航、路由等其他页面，为了修复一个问题，可能又会引入新的问题，然后需要继续回滚，重新修改。这个过程让我意识到，接手一个项目不能只看眼前的需求，最主要先熟悉项目的结构、运行方式、模块之间的关系和设计规范。

在实现一个需求时，应该先明确优先级。第一步应该先把核心功能实现并验证正确，确保基本流程能够正常运行。在这个基础上，再逐步完善前端样式、交互细节、视觉效果和不同设备的适配。如果一开始就同时关注功能、样式、动画、细节和各种情况，很容易导致开发重点不清晰，修改范围不断扩大，也会增加返工的概率。这一点也是我这周犯下的错误。后续我项目中我应该有一个明确的流程，先功能然后在实现体验，最后优化。

还有就是需求一定要记清楚、理解透。不能只记住大概目标，还要明确具体的页面。很多时候问题并不是不会实现，而是对需求记忆不完整，做到后面才发现遗漏了细节，或者修改方向和最初要求不一致，最后只能重新调整。这周也是，有部分内容在开会的时候提到，但是没有及时做记录，导致后续遗忘，又要在提醒。其次就是对需求有任何的不理解，应该及时提问沟通，不要按照自己的想法先做一版，这样后续又要返工。第三就是要养成详细的记录习惯，最好的方式就需要修改的地方（截图）加上详细的语言描述。

其次就是不能太全相信AI，这周的多次修改也是让我认识到了review，人工审查的重要性，每次完成一次修改、功能的新增，都不能只看目前单独修改的地方是否符合我的预期，还需要检查有没有对其他功能造成影响，这一点深有感触，codex在代码实现的能力上已经虽然说已经非常强大了，给它一个需求，它能快速准确的实现，并且自己测试。但是这部分是约束在这个功能上的，这周遇到了非常多次，如重构的时候希望整体风格替换成蓝色，codex就直接盖了一层蓝色的壳子上去，这个问题会导致后续页面缩放的时候，底色又漏了出来，修复这个问题后又导致导航的渲染消失，等等诸如此类的各种小问题。所以说，对公共样式、导航、布局、登录状态和路由相关的修改，更需要进行完整的回归检查。这周大部分时间花在就是因为修改之后没有及时、全面地查看，导致问题没有第一时间发现，后面又花了很多时间定位和修复。现在回头看，如果当时能够在每次修改后多花几分钟进行 review 和测试，很多问题其实可以提前避免。

复盘本周的开发过程，自己的不足主要体现在几个方面，一是对整体的项目结构还有修改需求理解还不够充分，有时候会过早进入修改阶段。二是在实现新功能或者修改的时候，只关注局部的结果，对整体的影响考虑的不够全面。三是完成修改后的review不够仔细，活干的很粗糙也不够心细，导致一些问题没有及时发现。

总的来说，这周虽然犯了不少错误，也经历了多次来回修改，但是这些问题让我对项目开发有了更加实际的认识，接下来的项目中我应该逐步改进自己的工作方式。希望把这些经验转化成后续的工作习惯，减少重复犯错，让自己的开发过程更加细致、稳定和高效。

### 四、页面刷新和加载优化

这周主要对项目的页面加载性能进行了优化，重点处理了会话请求重复、路由加载时机以及图片资源体积较大的问题。

**1. 会话请求去重**

页面启动时，多个组件可能会同时触发会话初始化请求。如果每个组件都单独发起请求，就会造成重复请求，也可能因为不同请求返回的时间不一致，导致页面状态被重复更新。

这次增加了会话请求去重处理：

```text
第一次请求会话
    ↓
保存正在进行中的请求
    ↓
其他组件需要相同数据时复用该请求
    ↓
请求完成后统一返回结果
```

如果同一个客户端已经存在正在执行的会话请求，后续请求会直接复用之前的 Promise，不再重复发送请求。请求完成后再清理对应状态，保证下一次需要重新初始化时能够正常执行。

同时还增加了超时处理，避免请求一直处于 pending 状态，导致页面长时间停留在加载阶段。

这样可以减少页面刚打开时的重复请求，也能让刷新后的加载过程更加稳定。

**2. 路由懒加载**

项目中门户、登录、控制台和文档页面包含的内容比较多，如果一开始就加载所有页面代码，会增加首次加载的资源体积，影响页面打开速度。

这次对路由加载方式进行了调整，根据用户当前访问的页面，再加载对应的页面模块。

路由懒加载的好处是：

- 减少首次加载时需要下载的代码；
- 避免用户还没有访问某个页面时提前加载对应资源；
- 让首页能够更快展示；
- 不同页面之间的代码边界更加清晰；
- 后续新增页面时不会明显增加首页的初始负担。

在调整懒加载的同时，也需要检查页面直接访问、刷新访问和页面跳转是否都能正常工作，避免只在应用内部点击时正常，直接刷新某个路径时出现加载失败。

**3. 图片资源压缩**

项目中使用了较多页面图片、产品截图和功能展示图，原始图片文件体积比较大，会影响页面加载速度，也会增加构建产物的大小。

这次对图片资源进行了压缩处理，并保留原始图片和压缩后的图片，方便后续需要时重新处理。

图片压缩主要解决了：

- 页面图片文件过大；
- 首次加载时资源下载时间较长；
- 构建产物体积较大；
- 图片资源不方便统一管理；
- 不同页面重复使用较大图片的问题。

压缩过程中需要在图片质量和文件大小之间进行平衡，不能单纯追求体积越小越好。如果压缩过度，会导致图片模糊、文字截图不清晰或者页面视觉效果下降。因此需要根据图片用途分别处理，产品截图和页面装饰图使用不同的压缩标准。



## 学习进度

### PostgreSQL 核心架构概览：它和 MySQL 有什么不同？

PostgreSQL 是一个开源的对象关系型数据库。它和 MySQL 一样支持表、SQL、事务、索引和权限，但更强调 SQL 标准、复杂查询、数据完整性以及扩展能力。

如果说 MySQL 常见于简单、高并发的 Web CRUD 场景，那么 PostgreSQL 更适合复杂业务、分析查询、地理空间数据和对数据一致性要求较高的系统。

### 一、PostgreSQL 的整体架构

PostgreSQL 采用多进程架构：

```text
客户端
  ↓
Postmaster
  ├── Backend Process
  ├── Background Writer
  ├── Checkpointer
  ├── WAL Writer
  └── Autovacuum
        ↕
    Shared Memory
    ├── Shared Buffers
    └── WAL Buffers
        ↕
    数据页 + WAL 文件
```

一个 PostgreSQL 实例由多个进程共同组成，并共享一块共享内存。Postmaster 负责管理实例和创建客户端连接进程。

### 二、Postmaster 和 Backend Process

Postmaster 是 PostgreSQL 实例的总管，主要负责：

- 监听端口，例如 `5432`
- 接受客户端连接
- 创建 Backend Process
- 启动和管理后台进程

每一个客户端连接通常对应一个 Backend Process。它负责处理该连接提交的 SQL，包括解析、优化、执行、事务和返回结果。

可以简单类比为：

```text
PostgreSQL：一个连接通常对应一个进程
MySQL：一个连接通常对应一个线程
```

因此 PostgreSQL 在连接数很多时通常需要使用连接池，例如 PgBouncer。

### 三、数据页和共享内存

数据库不会每次只读取一行数据，而是以数据页为单位读写。

PostgreSQL 的表和索引都由多个固定大小的数据页组成，默认通常为 8 KB：

```text
products 表
├── Page 0
├── Page 1
├── Page 2
└── Page 3
```

数据页中保存行数据、页头信息、行指针和空闲空间。

PostgreSQL 会把经常访问的数据页缓存到 Shared Buffers 中：

```text
磁盘数据页 → Shared Buffers → 查询读取
```

这和 MySQL InnoDB 的 Buffer Pool 类似。不过 PostgreSQL 同时也依赖操作系统文件缓存。

Shared Memory 中还会保存：

- Shared Buffers
- WAL Buffers
- 锁信息
- 事务状态
- 进程状态

### 四、B-Link 树和索引

PostgreSQL 默认的 B-tree 索引属于 B+Tree 的一种高并发实现，可以理解为带有横向链接的树结构：

```text
根节点
  ↓
中间节点
  ↓
叶子页 → 叶子页 → 叶子页
```

叶子页之间的链接可以支持范围查询，例如：

```sql
SELECT *
FROM products
WHERE price BETWEEN 100 AND 500;
```

数据库先定位到第一个叶子页，然后沿着叶子页继续扫描。

MySQL InnoDB 同样使用 B+Tree，因此两者的索引思想相近。主要差异是：

```text
InnoDB 主键索引叶子节点保存完整行数据
PostgreSQL 普通索引通常保存指向表行的 TID
```

所以 PostgreSQL 的索引查询经常需要：

```text
索引扫描 → 回表访问数据页
```

### 五、WAL 日志机制

WAL 是 Write-Ahead Logging，即预写式日志。

核心原则是：

```text
先写 WAL 日志，再写数据页
```

执行更新时，大致过程如下：

```text
修改内存中的数据页
      ↓
生成 WAL 记录
      ↓
WAL 刷盘
      ↓
事务提交
      ↓
数据页稍后写入磁盘
```

如果数据库在数据页写入磁盘前崩溃，重启后可以通过重放 WAL 恢复数据。

WAL 主要用于：

- 崩溃恢复
- 保证事务持久性
- 主从复制
- 时间点恢复
- 持续归档备份

它可以类比 MySQL InnoDB 的 Redo Log，但 PostgreSQL 的 MVCC 机制和 InnoDB 不完全相同。PostgreSQL 的旧版本行通常保留在表中，之后由 VACUUM 清理；InnoDB 则更多依赖 Undo Log 保存旧版本。

### 六、后台进程

PostgreSQL 中“后台进程”是一个总称，常见进程包括：

- Background Writer：逐步写回共享内存中的脏页
- Checkpointer：执行 checkpoint，确保数据页写入磁盘
- WAL Writer：把 WAL 缓冲写入 WAL 文件
- Autovacuum：清理旧版本行、更新统计信息
- Background Worker：为扩展、并行查询和逻辑复制提供后台执行能力

这些进程共同完成数据持久化、恢复、清理和维护工作。

### 七、数据访问层

数据访问层可以理解为 PostgreSQL 内部的 Access Method。它负责定义：

```text
数据如何存储
数据如何扫描
索引如何访问
```

查询：

```sql
SELECT *
FROM products
WHERE price > 100;
```

可能使用不同的访问方式：

```text
Seq Scan          顺序扫描
Index Scan        索引扫描
Bitmap Heap Scan  位图扫描
```

PostgreSQL 通过这种抽象支持多种索引和存储方式，例如：

```text
B-tree
Hash
GiST
GIN
BRIN
```

优化器会根据数据量、统计信息和查询条件选择合适的执行计划。可以使用下面的命令查看：

```sql
EXPLAIN
SELECT *
FROM products
WHERE price > 100;
```

### 八、SQL 查询和扩展能力

PostgreSQL 执行 SQL 的过程大致是：

```text
SQL
 ↓
解析
 ↓
语义分析和重写
 ↓
查询优化
 ↓
执行计划
 ↓
数据访问
 ↓
返回结果
```

它的优势不只是基础 CRUD，还包括：

- 复杂 JOIN
- CTE 和递归查询
- 窗口函数
- JSONB 查询
- 数组类型
- 全文搜索
- 并行查询
- 分区表
- 自定义函数和聚合

PostgreSQL 还允许扩展：

- 数据类型
- 函数
- 操作符
- 聚合函数
- 索引访问方法
- 后台进程
- 完整扩展包

例如：

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;

SELECT gen_random_uuid();
```

常见扩展包括：

```text
PostGIS              地理空间数据
pg_trgm              模糊匹配
pgcrypto             加密和 UUID
pg_stat_statements   SQL 执行统计
```
