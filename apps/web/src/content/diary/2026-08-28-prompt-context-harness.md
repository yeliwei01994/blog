本周主要围绕三个方向展开：完成坤元智算官网生态合作页面与首页的优化，继续梳理个人视觉分析平台的系统链路，同时学习提示词工程、上下文工程、驾驭工程、循环工程和节点工程。前两部分让我看到“一个系统如何落地”，最后一部分则帮助我理解“如何让 AI Agent 稳定地完成复杂任务”。

提示词工程解决的是“怎么把任务说清楚”；上下文工程解决的是“模型应该看到哪些信息”；驾驭工程解决的是“怎样让 Agent 在真实环境中稳定运行”；循环工程解决的是“怎样让系统根据反馈持续推进”；节点工程解决的是“如何把循环中的不同动作拆分、连接和协作”。它们共同构成了从一次对话到完整智能体系统的能力链路。

## 一、本周主要工作

### 1. 坤元智算官网：生态合作页面与首页优化

本周主要完成坤元智算官网生态合作页面、首页导航、首页算力资源卡片、快速开始助手和解决方案详情页加载体验的优化。这部分工作不是单纯修改几个页面样式，而是同时处理了信息结构、品牌视觉、路由关系、交互入口、资源加载和回归验证。

#### 页面建设

新增 `/partner` 生态合作页面，页面定位是向个人用户、开发者、创作者、AI 应用团队、模型厂商及科研公益团队介绍合作方式，并引导潜在伙伴提交合作方向。页面结构参考了国内算力平台的生态合作页面，但重新组织了适合坤元智算的内容和品牌表达。

页面由以下几个部分组成：

1. **Hero 首屏**：突出“连接算力与产业，共建智算新生态”的主题，通过主标题、说明文字和行动按钮快速说明页面用途。
2. **合作模式**：由原来的横向信息表格改成六张信息卡片，桌面端使用三列网格，移动端切换为单列，降低连续阅读压力。
3. **伙伴权益**：恢复 01、02、03、04 编号卡片布局，分别表达算力能力、技术扶持、联合推广和生态共建等合作价值，并使用大号背景编号增加层次。
4. **合作流程**：整理为“提交合作方向 → 完成技术与业务沟通 → 开启项目协同与长期合作”三个步骤，让用户知道提交信息后会经历什么。
5. **底部 CTA**：改成独立的蓝色渐变圆角块，与上下内容保持留白，避免使用一整条满宽色块造成页面结束过于生硬。

这次还明确移除了“生态伙伴案例”和“查看更多合作场景”入口。这样做不是减少内容，而是暂时去掉缺少真实业务资料、容易形成空壳的模块，先保证页面信息真实、结构完整，后续再根据实际合作案例补充。

#### Hero 视觉和品牌色彩

Hero 使用蓝色数字地平线背景，设计重点包括：

- 蓝色作为主基调，用深蓝、蔚蓝和青色高光表达科技感，并与官网现有品牌体系保持一致。
- 中心区域保持低细节，为居中的中文标题和按钮留出可读空间。
- 两侧和底部保留网络节点、数据流和数字结构，让背景承担氛围表达，而不是抢夺信息层级。
- 图片本身不生成 Logo、文字、水印或 UI 面板，避免图片文字与页面真实文案重复。
- 桌面端优先保证宽屏效果，同时考虑移动端裁切后标题不会被复杂纹理干扰。

之前页面中偏紫色的元素已经统一调整为坤元智算的蓝色体系。这样页面视觉更加稳定，也避免单独的合作页面与官网其他页面产生明显割裂。

#### 导航与交互调整

首页和合作页面的导航同步进行了调整：

- 移除“软件产品”主导航入口，但保留软件产品页面和路由，避免已有链接失效。
- 在原导航位置接入“生态合作”，桌面端和移动端保持入口关系一致。
- 合作页面首屏使用透明导航叠加在 Hero 背景上，滚动后切换成与首页一致的白色背景导航。
- 恢复“联系我们”作为顶部导航入口，不再把“快速开始”放在主导航中。

“快速开始”改成全站右下角悬浮的“坤元小助手”。浮动入口只保留聊天符号，不显示额外文字和 Logo；点击后展开助手面板，面板内保留欢迎语、聊天记录和四个快捷问题：

- 我想了解算力服务
- 帮我分析一个 AI 产品需求
- 我需要搭建行业解决方案
- 帮我生成一个坤元智算的企业宣传图

当前没有增加输入框和发送按钮，用户通过预设问题触发演示流程。对话内容在浮层内部滚动，不会把页面整体撑长；宣传图快捷项会在回复中展示企业宣传图。这个方案更适合当前以展示和引导为主的官网阶段，后续如果接入真实客服或 AI 服务，再扩展自由输入能力。

#### 首页算力资源卡片

首页算力资源区域的问题主要不是价格数据错误，而是信息层级不够明显：普通资源卡片之间区分度较低，边框和分隔线颜色接近，小字号参数对比度偏低，不同计费方式放在一起时不容易横向比较，CTA 卡片与普通资源卡片的角色差异也不够突出。

本次没有修改价格数据和核心交互逻辑，主要调整视觉表达：

- 普通卡片增加渐变背景和更清晰的边框；
- 增加 hover 上浮和阴影效果，强化卡片可交互的反馈；
- GPU 标签保持右对齐，避免与价格和名称争夺视觉焦点；
- 提升价格、参数说明和底部分隔线的可读性；
- CTA 卡使用更明显的蓝色渐变、发光边框和阴影；
- CTA 按钮改为更清晰的实心主按钮，并增强 hover 状态。

这部分的目标不是增加装饰，而是让用户更容易区分普通资源、价格信息和主要行动入口。

#### 解决方案详情页的加载体验

针对首页“自研 IB 网络解决方案”和“超节点集群建设方案”点击后短暂闪现、体感像卡顿的问题，使用浏览器 Network 面板分析首次加载过程。排查后发现：

- 详情页采用 React 路由级懒加载，用户点击后才请求对应页面代码包。
- 两个详情页页面代码包约 5 KB，相关拓扑 SVG 约 5 KB，响应速度较快，不是主要瓶颈。
- 导航 Logo 原文件约 33 KB，首次请求下载耗时约 1.95 秒，是当时最明显的资源传输瓶颈。
- Logo 请求使用生产静态资源路径并返回 200，问题主要在资源体积和懒加载时机，而不是接口代理错误。

对应的处理分为三部分：

1. 使用项目现有图片压缩脚本压缩 Logo 及相关 PNG/JPG，将导航 Logo 从约 33 KB 压缩到约 4.8 KB，原始资源备份到 `assets-original`，方便恢复和对比。
2. 新增统一的解决方案页面预加载模块，在鼠标移入、键盘聚焦和触摸开始时提前加载目标页面代码。用户真正点击时，页面 chunk 通常已经准备完成。
3. 移除会让等待感更明显的旋转加载图标，只保留不可见的固定高度占位，避免加载期间页面布局跳动。

同时在 `index.html` 中增加 favicon 配置，直接复用现有 Logo 标志图，避免重复维护一份品牌图形资源。

#### 视觉设计经验
学习了一下常见的设计比例
- 黄金比例：`1:1.618`，适合强调自然、优雅和动态。
- 白银比例：`1:√2`，适合纸张和结构化系统。
- `1.25`（小三度）适合温和、紧凑的字号与间距层级。
- `1.333`（大三度）层次清晰，适合一般网页排版。
- `1.5`（纯四度）适合拉开标题与正文、卡片与留白的差异。
- `1.618`适合更有张力的标题和版式层级；`2`适合形成强烈的视觉对比。

实际落地时，UI 界面优先使用 `4px、8px、12px、16px、24px、32px` 的间距倍数；海报更常用 `2:3、3:4、4:5`；网页横幅可使用 `16:9` 或 `3:1`，需要电影感时使用 `21:9`。正文为 `16px` 时，标题可以按 `1.25、1.333、1.5` 倍递进；分栏则可以尝试 `1:1、1:2、2:3、3:5`，不必执着于黄金分割。


### 2. 个人视觉分析平台：从功能开发转向完整闭环

个人视觉分析平台这部分工作，重点不是单独增加一个识别接口，而是把视频从上传到事件审核、证据查看和回放的链路串起来。系统目标可以概括为：上传一段视频后，后台能够异步分析，识别结果能够转化为业务事件，用户能够解释、审核、追踪和回放这些事件。

#### 系统架构与职责边界

整体架构可以分为前端、网关、API、消息队列、持久化存储、媒体文件和分析 Worker：

```text
浏览器 / React
       │ HTTP、JSON、multipart
       ▼
Nginx：静态文件、API 反向代理、媒体访问
       │
       ├── Rust API：鉴权、上传、任务和查询
       ├── MySQL：任务、事件、规则和审核事实
       ├── Redis Stream：vision:jobs 异步任务消息
       └── media：原始视频、抽帧证据和回放文件
                         │
                         ▼
                Worker：FFmpeg → YOLO → 规则引擎
```

各组件的边界需要保持清晰：Nginx 负责统一入口、React 静态文件、API 代理和媒体访问；Rust API 负责鉴权、文件接收、任务创建、状态查询和审核接口；Redis 只负责异步任务通知和短期队列状态；MySQL 负责长期保存任务、事件、规则和审核历史；视频及证据图片放在共享媒体目录，生产环境可以替换成对象存储；Worker 承担耗时的抽帧、模型推理和事件生成；Docker 则统一服务网络、运行时环境、数据卷和启动依赖。

这里最重要的数据原则是：**MySQL 保存事实，Redis 负责调度，媒体卷保存文件，Worker 执行计算，Nginx 提供访问入口。** Redis 不能作为最终结果的唯一存储，MySQL 也不应该承担大文件存储和高频队列消费。

#### 一次视频任务的完整流程

一次上传任务大致经过以下步骤：

1. React 通过 `POST /api/v1/videos/upload` 发送视频文件。
2. API 清理上传文件名，避免路径穿越，并将视频写入媒体目录。
3. API 读取视频时长，在 MySQL 创建 `video_jobs` 任务记录。
4. API 向 Redis Stream `vision:jobs` 写入包含 `job_id` 的消息，然后尽快返回任务信息。
5. Worker 从 Stream 消费任务，根据 `job_id` 加载任务、规则和视频路径。
6. Worker 使用 FFmpeg 抽取 JPEG 帧，将帧发送给 YOLO 服务进行识别。
7. 规则引擎根据目标类别、置信度、区域和持续时间生成业务事件。
8. Worker 将事件、检测对象和证据写入数据库，并更新任务进度和最终状态。
9. React 轮询 `GET /api/v1/jobs/{id}`，任务完成后刷新事件列表。

这种拆分把“API 快速接收任务”和“后台长时间计算”分开。即使视频分析需要几十秒，上传接口也不需要一直占用 HTTP 请求；多个视频同时上传时，也可以通过 Redis 排队并增加 Worker 数量来扩展处理能力。

#### 任务、Worker 和媒体管理

任务状态不应只用一个布尔值表示，而需要有明确的生命周期，例如：

```text
pending → processing → completed
                    └→ failed
                    └→ cancelled
```

任务记录至少需要保存任务名称、视频文件名、时长、状态、进度、源文件路径、创建时间、更新时间和软删除时间。任务支持重命名、删除和软删除时，还要区分数据库记录、原始视频和检测回放，不能因为删除一条任务误删其他任务的媒体文件。

Worker 在 `WORKER_MODE=1` 时消费 Redis Stream。它需要把 YOLO 返回的检测类别、置信度、边界框、时间戳和模型版本转换成平台内部结构。边界框还要同时兼容像素坐标和 `0～1` 的归一化坐标，否则会出现识别框位置偏移。视频时长、抽帧进度和当前批次也要写回任务状态，便于前端展示进度和排查失败位置。

#### 规则引擎、区域和事件证据

模型输出本身不是最终业务结果。平台还需要通过规则把检测结果转成用户能够理解的事件，目前重点梳理了人员停留、人员进入区域和最大人员数量等规则：

| 规则 | 关注内容 | 关键条件 |
|---|---|---|
| 人员停留 | 人员在画面中持续出现 | 类别、最低置信度、最短持续时间 |
| 人员进入区域 | 人员是否进入指定区域 | 区域形状、目标中心点、进入时间 |
| 最大人员数量 | 同时出现的人数是否超限 | 人数上限、统计窗口、置信度 |

规则中的最低置信度、最短持续时间、人数上限、启用状态和版本应该保存到 `event_rules`，而不是全部写死在 Worker 中。Worker 开始任务前从 MySQL 刷新规则，确保用户保存的新配置能够应用到新任务，而不是继续使用旧的内存配置。

区域编辑支持鼠标拖动绘制矩形和多边形，也支持空白画布和视频证据作为背景。之前“重置区域后点击应用区域没有效果”的问题，根本上涉及前端状态、保存动作和 Worker 配置是否一致；修复后，区域保存和应用能够按照新的配置执行。区域外目标仍触发事件的问题也进行了修复，鼠标绘制过程增加节流，避免频繁更新导致卡顿或黑屏。

事件证据不再使用占位图片，而是保存真实抽帧结果，例如：

```text
media/evidence/<event-id>/
```

每个事件关联时间点、证据帧、检测框和目标信息。前端可以显示“人员 11 次检测 · 平均置信度 34%”这类中文摘要，并把内部事件类型转换为更容易理解的文字：

```text
person_stay        → 人员停留
person_enter_zone  → 人员进入区域
person_count_limit → 最大人员数量
```

#### 事件审核、查询和回放

事件结果需要进入业务审核，而不是停留在模型输出页面。审核状态可以从待复核进入确认或忽略，再进入已处置和已关闭；需要再次处理时也可以进入处理中。审核操作保存审核人、备注、处置结果、旧状态、新状态和审核时间，详情页通过时间线展示完整的变化过程。

审核按钮还需要处理处理中状态、成功和失败提示，以及重复提交保护。事件列表增加组合查询、分页、排序、CSV 导出和 HTML 报告接口，使事件能够被筛选、确认、追踪和交付。

回放时需要把事件的 `start_time_ms`、`end_time_ms` 和视频真实时长统一起来。前端不能只根据事件数量或当前页面状态猜测时间轴；如果 FFprobe 获取时长异常，需要从视频容器格式、编码信息和读取方式一起排查。只有事件时间、证据帧和原始视频保持一致，用户才能从事件列表跳转到准确的回放位置。

#### 性能和可靠性优化

视频分析是一个长任务，前端和 Worker 都需要控制资源使用：

- **轮询退避**：任务状态轮询从固定每秒一次调整为 `1 秒 → 2 秒 → 3 秒 → 4 秒 → 5 秒`，状态发生变化时恢复较短间隔，长时间不变时降低请求频率。
- **限制事件查询数量**：事件列表接口增加 `limit` 参数，默认最多返回 50 条，避免数据增长后一次返回过多内容。
- **流式上传**：视频按数据块写入临时文件，上传完成并校验后再切换成最终文件；失败时清理临时文件，避免留下不完整视频。
- **降低检测频率**：默认检测间隔由 100ms 调整为 200ms，并支持 `DETECTION_INTERVAL_MS` 配置，范围为 100ms 至 5000ms。间隔太大可能漏掉短事件，需要结合真实视频验证。
- **YOLO 批量推理**：新增 `POST /v1/infer/batch`，一次发送多张帧图片及其 `frame_id`、`timestamp_ms`，默认批量大小为 4，减少逐帧 HTTP 请求和模型调用开销。
- **并发上限**：Worker 默认最多同时执行 2 个批次，`YOLO_CONCURRENCY` 限制在 1 至 4，批量大小限制在 1 至 16，避免配置过大造成显存或内存压力。

#### 视频平台性能实测与进一步优化

在完成批量推理和并发处理后，又使用同一类视频任务进行了多组对比测试。每组任务处理 44 帧，产生 121 个检测结果和 3 个事件，所有任务均成功完成且没有错误。

| 配置 | Batch | 并发数 | 总耗时 | 相对基线 | 加速比 |
|---|---:|---:|---:|---:|---:|
| 基线 | 1 | 1 | 43.702 秒 | 100% | 1.00x |
| 批量并发 | 4 | 2 | 25.023 秒 | 57.3% | 1.75x |
| 大 Batch 并发 | 8 | 2 | 24.645 秒 | 56.4% | 1.77x |
| 高并发 | 8 | 4 | 25.740 秒 | 58.9% | 1.70x |

从整体结果看，`8/2` 是当前测试中的最佳配置：总耗时比 `1/1` 减少约 19.057 秒，下降 43.6%。`4/2` 已经获得了大部分收益，`8/2` 只进一步减少约 378ms；当并发数从 2 提高到 4 后，耗时反而增加约 1.095 秒，说明并发并不是越高越好。

各阶段耗时对比进一步说明了性能变化：

| 阶段 | `1/1` | `4/2` | `8/2` | `8/4` | 结论 |
|---|---:|---:|---:|---:|---|
| 视频探测 | 94ms | 75ms | 88ms | 80ms | 影响很小 |
| 抽帧 | 468ms | 272ms | 274ms | 263ms | 不是主要瓶颈 |
| YOLO 推理 | 20.250s | 2.121s | 2.088s | 2.174s | 批量处理收益明显 |
| 规则分析 | 3.081s | 3.108s | 3.004s | 3.042s | 基本稳定 |
| 证据保存 | 3.048s | 3.067s | 2.972s | 3.012s | 基本稳定 |
| 标注视频编码 | 19.748s | 19.396s | 19.134s | 20.116s | 后续优化重点 |

最明显的变化发生在 YOLO 阶段：逐帧调用时需要处理 44 个批次，推理耗时约 20.250 秒；使用 `batch=4、concurrency=2` 后，批次数减少为 11，YOLO 耗时降到 2.121 秒；使用 `batch=8、concurrency=2` 后进一步降到 2.088 秒。此时 YOLO 只占总耗时约 8.5%，已经不再是系统的主要瓶颈。并发提高到 4 后，CPU 或线程竞争开始出现，还影响了视频编码阶段。

#### 标注视频编码的瓶颈定位

批量推理优化后，总耗时仍然在 24 秒左右，说明瓶颈已经从模型推理转移到了 `annotated_video_encode`。这个阶段并不只是“调用一次 FFmpeg”，实际包含四个步骤：

```text
重新读取原始 JPG
  → 在检测帧上绘制边界框、类别和时间
  → 将检测帧复制成完整的视频帧数量
  → 调用 FFmpeg 编码 MP4
```

首先调整 FFmpeg 参数：

```text
preset=veryfast
CRF=28
```

这一步牺牲少量画质，换取更快的编码速度和更小的文件体积，使标注视频编码阶段从约 19.134 秒降到 17.617 秒，总耗时降到 23.784 秒。但继续拆分阶段后发现，真正耗时的并不是 FFmpeg 本身，而是逐帧绘制标注：

```text
annotate_frames：17.156 秒
ffmpeg_encode：0.990 秒
duplicate_frames：0.113 秒
```

因此将优化重点转向标注帧并行处理，通过 `ANNOTATION_CONCURRENCY=4` 同时处理多张检测帧。对比结果如下：

| 指标 | 并行前 | 并行后 | 变化 |
|---|---:|---:|---:|
| 总耗时 | 24.015 秒 | 11.083 秒 | 减少 53.8% |
| `annotate_frames` | 17.156 秒 | 4.403 秒 | 减少 74.3% |
| `annotated_video_encode` | 18.308 秒 | 5.624 秒 | 减少 69.3% |
| `duplicate_frames` | 113ms | 97ms | 基本不变 |
| `ffmpeg_encode` | 990ms | 1.070 秒 | 基本不变 |
| YOLO 推理 | 2.333 秒 | 2.101 秒 | 基本不变 |
| 检测数 | 121 | 121 | 结果一致 |
| 事件数 | 3 | 3 | 结果一致 |

这组结果说明，视频平台的优化顺序应该是先用性能数据定位瓶颈，再决定增加 Batch、模型并发还是帧处理并发。批量推理解决了逐帧调用模型的开销；标注帧并行解决了 CPU 图像处理的开销；而 FFmpeg 编码本身已经只占较小比例，继续单独调编码参数的收益有限。

#### 性能优化后的阶段性结论

目前视频分析平台已经形成了比较明确的优化路径：

```text
逐帧 YOLO 推理
  → Batch + Worker 并发
  → YOLO 不再是主要瓶颈
  → 拆分标注视频生成阶段
  → 标注帧并行处理
  → 总耗时从约 44 秒降到约 11 秒
```

后续还需要继续观察不同视频分辨率、帧数、编码格式和 GPU/CPU 环境下的结果，避免把当前单个样本的最佳参数直接当成所有场景的固定配置。同时需要持续记录每个阶段耗时、检测数量、事件数量和错误数，确保性能提升没有以检测结果不一致或事件遗漏为代价。



## 二、学习Agent底层工程思维

可以先用一个简单的类比来理解：如果把 AI Agent 比作一匹能力很强但不完全可预测的马，那么：

```text
提示词工程：告诉它应该往哪里走
上下文工程：给它地图、路况和任务资料
驾驭工程：修建道路、设置护栏、安排补给，并检查它是否真的到达目的地
```

这几个概念的关注范围逐步扩大：

| 工程层次 | 核心问题 | 主要优化对象 | 典型交互方式 |
|---|---|---|---|
| 提示词工程 | 怎么把话说清楚？ | 指令、角色、示例、格式和限制 | 一问一答 |
| 上下文工程 | 模型需要知道什么？ | 历史、文档、记忆、检索结果和工具输出 | 信息注入后生成 |
| 驾驭工程 | Agent 如何可靠完成任务？ | 工作流、权限、状态、测试、反馈和监控 | 多步骤持续执行 |
| 循环工程 | 如何让任务持续推进？ | 触发器、观察、调整、停止条件和记忆 | 反馈闭环 |
| 节点工程 | 任务应该如何拆分？ | 节点输入、输出、分支和连接关系 | 工作流编排 |


这几个层次之间的逻辑关系是逐步扩展的：首先，提示词工程把任务、角色、要求和输出标准说清楚；然后，上下文工程为模型准备完成任务所需的资料、历史和工具结果；驾驭工程为 Agent 接入工具、状态和验证机制；循环工程让它根据观察结果不断调整，直到完成、暂停或交给人处理；节点工程则把循环中的动作拆分成可组合的单元，并明确它们之间的连接、分支和协作关系。

因此，提示词工程是交互起点，上下文工程是信息基础，驾驭工程是运行保障，循环工程是持续改进机制，节点工程是把复杂动作组织起来的流程结构。前面的层次解决“模型是否理解、是否拥有足够信息”，后面的层次继续解决“任务如何执行、结果如何验证、系统如何持续推进以及多个动作如何协作”。

## 三、提示词工程：把任务说明白

### 1. 提示词工程是什么

提示词工程是设计、优化和测试输入指令的过程，目标是让 AI 更准确地理解任务，并按照预期的方式输出结果。

它并不是寻找某一句“神奇咒语”，而是把原本模糊的需求变成一份清晰的任务说明书。提示词越能明确任务目标、背景、边界和验收标准，模型越容易给出可用结果。

例如，下面的提示词比较模糊：

```text
帮我写个方案。
```

改进后可以写成：

```text
你是一名市场营销顾问。

请为一款面向大学生的记账 App 制定推广方案，包含：
1. 目标用户
2. 用户痛点
3. 推广渠道
4. 活动创意
5. 预算建议

要求：
- 使用 Markdown 标题和表格输出；
- 每个部分给出可执行的建议；
- 不超过 1000 字；
- 不要使用空泛的宣传口号。
```

后一个版本并没有使用复杂术语，但它交代了角色、任务、内容范围、输出格式和限制条件，因此更容易得到稳定结果。

### 2. 四要素框架

写提示词时，可以先检查下面四个要素：

| 要素 | 需要思考的问题 | 示例 |
|---|---|---|
| 角色 | AI 应该以什么身份回答？ | 资深产品经理、英语教师 |
| 指令 | AI 具体要做什么？ | 总结、分析、翻译、生成 |
| 背景 | AI 需要知道哪些前提？ | 读者、用途、已有资料 |
| 限制 | 有什么边界和标准？ | 字数、格式、禁用内容、判断条件 |

角色设定可以帮助模型采用合适的知识角度和表达方式，但角色不是越夸张越好。比起“你是世界上最厉害的专家”，更有效的是说明专业领域、行为方式和判断原则：

```text
你是一名有 8 年经验的产品经理，擅长 B2B SaaS 产品。
回答时先给结论，再说明依据；涉及方案时同时考虑成本、风险和实施难度。
```

### 3. 用示例和模板控制输出

当用户希望 AI 按固定格式写作、分类或提取数据时，给出示例通常比抽象描述更有效。这种方法通常称为少样本学习（Few-shot Learning）。

好的示例需要满足三个条件：

- 覆盖任务中常见的情况；
- 输入和输出格式保持一致；
- 示例本身就是理想结果，而不是随意拼凑的内容。

如果格式非常重要，可以直接提供模板：

```text
请使用以下模板输出：

## 产品分析

### 核心优势
- [优势 1]
- [优势 2]

### 主要风险
- [风险 1]
- [风险 2]

### 综合建议
[一句话结论]
```

### 4. 让模型给证据，而不是只给结论

对于分析、判断和事实性任务，应该要求模型先提取依据，再做判断。例如：

```text
请先列出支持结论的关键事实，再给出最终判断。
如果提供的资料不足，请明确说明无法判断，不要自行补充。
```

这里的重点不是强迫模型展示全部内部思考，而是让输出包含可检查的证据和判断依据。这样更容易发现模型是不是漏看资料，或者先有结论、再为结论寻找理由。

### 5. 提示词工程的边界

提示词工程能够改善模型的行为，但不能解决所有问题：

- 再好的指令也无法替代缺失的业务资料；
- 不能仅靠提示词保证事实永远正确；
- 复杂任务如果只用一条超长提示词，仍然可能遗漏步骤；
- 需要实时数据时，必须接入检索、数据库或工具；
- 在医疗、法律和财务场景中，必须进行专业核实。

因此，提示词工程更像是 AI 应用的语言接口，而不是完整的可靠性方案。



## 四、上下文工程：管理模型的工作记忆

### 1. 上下文不只是提示词

上下文是模型生成回答前能够看到的全部信息，通常包括：

```text
系统指令
用户输入
历史对话
项目文档
当前代码
检索结果
用户偏好
工具返回值
任务状态
```

提示词只是上下文的一部分。提示词工程主要关注“这条指令怎么写”，上下文工程则关注“现在应该把哪些信息放进模型的工作区”。

例如，让 Agent 修改一个大型项目时，真正有价值的上下文可能包括：项目目录结构、相关模块代码、接口约定、数据库结构、错误日志、测试命令和之前已经做过的修改。只给一句“帮我修复这个项目”，即使指令没有语法问题，模型也缺少完成任务所需要的材料。

### 2. 上下文是有限资源

模型的上下文窗口有容量限制，而且信息越多不一定越好。无关资料、重复历史和过时文档会挤占真正重要的信息，导致模型注意力下降、前后矛盾或遗漏关键条件。

因此，上下文工程的目标不是“把所有资料都塞进去”，而是：

```text
在有限的上下文窗口中，选择最相关、最新、可信且足够完成任务的信息。
```

常见操作包括：

- 召回：从文档库、数据库或代码库中找到相关内容；
- 过滤：删除与当前任务无关或重复的信息；
- 压缩：把长历史、日志和文档提炼成摘要；
- 排序：把最重要的任务、约束和证据放在更容易被关注的位置；
- 组装：按照模型更容易理解的顺序构造完整输入；
- 外部存储：把不适合长期放入上下文的信息保存到数据库或文件中，按需读取。

### 3. 上下文工程的常见组成

一个较完整的上下文系统通常包含：

| 组件 | 作用 |
|---|---|
| 系统指令 | 定义身份、原则和行为边界 |
| 短期记忆 | 保存当前对话和当前任务状态 |
| 长期记忆 | 保存用户偏好、历史决策和稳定知识 |
| 检索系统 | 从文档、数据库或 API 获取相关资料 |
| 工具编排 | 管理工具调用及其结果如何回到上下文 |
| 查询增强 | 将模糊问题转换为更适合检索的请求 |
| 输出结构 | 让结果可以被后续步骤继续使用 |

### 4. 资料和指令要分离

当模型需要分析外部文本、用户输入或网页内容时，可以使用语义化标签区分指令与数据：

```text
请只根据 <reference> 中的内容回答 <question>。
如果参考资料不足，请说明无法判断。

<reference>
这里是需要参考的文档内容。
</reference>

<question>
这里是具体问题。
</question>
```

这种组织方式可以减少混淆，也有助于防范外部文本中的提示词注入。标签名称最好能表达内容性质，例如使用 `<contract>`、`<code>`、`<resume>`，而不是笼统的 `<text1>`、`<text2>`。

## 五、驾驭工程：让 Agent 稳定完成工作

### 1. 驾驭工程是什么

Harness Engineering（驾驭工程）关注的是围绕 AI Agent 建立一整套约束、反馈、编排和控制机制。它不直接训练模型，而是设计模型运行的环境，让 Agent 能够在真实任务中保持方向、接受检查并从失败中恢复。

它的核心思想可以概括为：

> 人类掌舵，智能体执行。

当 Agent 从“一次回答”变成“连续完成几十个步骤”时，问题就不再只是提示词是否写得好，而是：

- 它是否知道任务做到哪一步？
- 它是否可以访问不该访问的资源？
- 它是否有明确的完成标准？
- 它是否真的运行了测试？
- 失败后是否能够回到正确步骤？
- 长时间运行后是否会积累混乱和技术债务？

### 2. Agent 的典型失败模式

长任务中，Agent 常见的失败方式包括：

1. **试图一步完成所有事情**：上下文很快膨胀，任务中途产生半成品，下一轮又无法理解之前做了什么。
2. **过早宣布任务完成**：看到局部结果正常，就忽略了还没有完成的功能和边界情况。
3. **写完代码就认为功能完成**：单元测试或单个接口请求通过，并不代表端到端流程真的可用。
4. **复制代码库中的坏模式**：Agent 很擅长模仿，如果项目中存在混乱的结构，它也会快速复制并放大问题。
5. **进入无效循环**：反复尝试相同的修复方法，却没有记录失败原因，也没有改变策略。

这些问题说明，单纯增加提示词长度并不能解决 Agent 的长期可靠性问题，需要从运行环境和流程上增加护栏。

### 3. 四类核心护栏

#### 上下文护栏：让 Agent 知道该看什么

项目说明文件、任务文档和按需检索机制可以帮助 Agent 快速理解工作范围。文档不应该变成一份越来越长、无人维护的规则清单，而应该保留稳定入口，并能链接到更具体的说明。

一份好的项目指南通常应该说明：

- 项目如何启动和测试；
- 目录和模块分别负责什么；
- 哪些规则必须遵守；
- 哪些文件可以修改；
- 完成任务前必须执行哪些验证。

更重要的是，文档应该随着 Agent 的失败案例持续更新。每一次失败都可以反过来推动项目环境变得更清晰。

#### 架构护栏：让错误难以进入系统

架构规则不能只写在文档里，还可以通过类型系统、Linter、依赖检查和 CI 自动执行。例如规定模块只能按照下面的方向依赖：

```text
Types → Config → Repo → Service → Runtime → UI
```

如果下层模块反向依赖上层模块，CI 可以直接阻止合并。这里的错误信息也应该告诉 Agent 为什么违反规则、正确方式是什么，而不是只显示一个难以理解的错误编号。

#### 反馈护栏：让 Agent 知道自己做错了

测试、Lint、类型检查、浏览器验证和代码审查都可以组成反馈回路：

```text
执行任务 → 运行验证 → 收集错误 → 返回 Agent → 修复 → 再次验证
```

反馈必须足够具体。如果只告诉 Agent“失败了”，它很可能继续猜测；如果把失败命令、错误位置、预期结果和实际结果一并提供，它才更容易进行针对性修复。

#### 熵管理护栏：持续清理系统混乱

随着代码、文档和配置不断变化，系统会产生技术债务、过时文档、重复实现和架构偏差。驾驭工程不应该等问题积累到很严重时再集中处理，而应当像垃圾回收一样持续进行小规模清理。

可以定期扫描：

- 文档与代码是否一致；
- 是否存在重复或废弃模块；
- 是否违反架构依赖规则；
- 测试是否覆盖关键路径；
- 任务记录和实际状态是否一致。

### 4. 驾驭工程与传统 Agent 框架的关系

传统 Agent 框架主要帮助开发者构建智能体，例如定义消息路由、工具调用和任务生命周期。驾驭工程关注的则是智能体运行起来以后如何保持可靠：如何保存状态、如何重放任务、如何限制成本、如何监控过程、如何恢复错误以及如何在没有人工盯守的情况下完成验证。

因此，驾驭工程不是 SDK 或框架的替代品，而是位于模型和 Agent 框架之上的运行控制层。

## 六、循环工程：让系统持续推进目标

### 1. 什么是循环工程

循环工程（Loop Engineering）关注的是如何设计、运行和改进一个反馈闭环，让 Agent 不只是执行一次，而是能够持续规划、行动、观察结果、修复问题，直到达到明确的完成条件。

它与提示词工程的区别在于：提示词工程优化一条指令的质量，循环工程优化“什么时候提示、接下来做什么、结果是否合格、什么时候停止”的完整过程。

一个基本循环可以分成五个阶段：

1. **意图**：明确目标、范围和成功标准；
2. **上下文**：收集当前任务所需的代码、文档、历史和工具结果；
3. **行动**：修改文件、调用工具、运行命令或生成方案；
4. **观察**：读取测试结果、编译错误、运行日志或人工 Review；
5. **调整**：根据观察更新计划，继续下一轮，或者在满足条件时停止。

循环的关键不在“重复调用模型”，而在于每一轮都能获得新的有效反馈。测试失败、类型错误和 Review 意见都应该转化为下一轮的上下文，而不是被简单地丢弃。

### 2. 内循环与外循环

Agent 自己完成“读文件、修改代码、运行测试、处理错误”的过程，可以看作内循环。循环工程设计的是更高一层的外循环：发现任务、分派 Agent、保存状态、检查结果，并决定是否开启下一轮。

```text
内循环：感知 → 推理 → 行动 → 观察 → 再行动
外循环：发现任务 → 分派执行 → 验证结果 → 记录状态 → 开启下一轮
```

这也是“从手动提示 Agent”走向“设计一个系统来提示 Agent”的变化。人不再需要亲自推动每一步，但仍然需要设计目标、约束、验证方式和停止条件。

### 3. 循环工程的关键组成

一个可以长期运行的 Loop 通常需要：

- 自动触发器：决定什么时候启动任务；
- 节点和工作流：规定每轮要执行哪些动作；
- 上下文刷新：在关键观察后重新收集相关信息；
- 持久记忆：保存任务状态、已尝试方案和未解决问题；
- 验证器：检查输出是否满足完成条件；
- 权限控制：限制工具和外部操作的范围；
- 失败恢复：设置重试、回退、暂停和人工介入机制。

例如，修复一个 Bug 的循环不应该只是：

```text
让 Agent 修复 Bug → Agent 说已经修复
```

更可靠的设计是：

```text
读取失败测试 → 分析原因 → 修改代码 → 运行测试
    ↑                                  ↓
    └──── 测试失败：记录错误并进入下一轮 ────┘
                         ↓
                 测试通过并完成人工确认
```

### 4. 循环工程的风险

循环会放大系统原本的优点和缺点。目标不清晰时，Agent 可能反复空转；验证信号不可靠时，Agent 可能“通过了测试但没有解决真实问题”；上下文没有刷新时，它会基于过期假设继续工作；权限过大时，错误可能被自动扩大。

因此，循环工程必须遵守几个原则：

- 从范围很小、结果可验证的任务开始；
- 明确写出停止条件，而不是只写“把问题修好”；
- 优先采用小范围、可回退的修改；
- 自动验证和人工审查同时保留；
- 对循环次数、成本、超时和权限设置上限；
- 把失败案例沉淀为新的规则、节点或上下文资料。

## 七、节点工程：把任务拆成可组合的单元

### 1. 什么是节点工程

理解循环之后，再看节点会更自然：循环负责让系统持续推进，节点则是循环中可以被调用、验证和组合的具体工作单元。节点工程关注的是，一个复杂任务应该拆成哪些步骤，以及这些步骤如何通过状态、条件和输出连接起来。

在工作流或 Agent 系统中，一个节点通常代表一次明确的动作，例如接收输入、检索资料、调用模型、执行工具、校验结果或请求人工确认。节点工程的核心不是把流程画得复杂，而是让每个节点都有清晰的输入、处理逻辑、输出和失败处理方式。

### 2. 节点应该如何设计

一个可靠的节点至少应该明确下面几件事：

| 设计内容 | 需要回答的问题 |
|---|---|
| 输入 | 节点需要哪些数据？数据来自用户、上一个节点还是外部工具？ |
| 处理 | 节点具体完成什么动作？使用模型、规则还是普通代码？ |
| 输出 | 后续节点需要什么结构和字段？ |
| 失败 | 输入无效、调用失败或结果不合格时怎么办？ |
| 验证 | 如何判断节点已经完成并且结果可信？ |
| 权限 | 节点是否可以写文件、调用接口或执行高风险操作？ |

例如，一个资料问答流程可以拆成：

```text
用户问题
  → 问题改写节点
  → 知识检索节点
  → 证据筛选节点
  → 回答生成节点
  → 引用与格式校验节点
  → 最终回复
```

这里的每个节点都有相对单一的职责。检索失败时可以重试或提示资料不足，格式校验失败时可以重新生成，而不需要让整个流程从头开始。

### 3. 节点工程与 Agent 的关系

并不是所有节点都必须由大模型完成。确定性强的任务，例如字段校验、权限判断、数值计算和状态更新，通常更适合使用普通代码或规则；需要理解自然语言、处理模糊意图和进行开放式判断的部分，才适合交给模型或 Agent。

因此，节点设计需要在“智能”和“确定性”之间做取舍：

- 固定规则优先使用代码或工作流节点；
- 需要理解和规划时使用模型节点或 Agent 节点；
- 有副作用的动作前增加校验和人工确认节点；
- 每个节点尽量只做一件能够被验证的事情。

知乎相关文章中也强调，企业级 Agent 通常不是单个模型调用，而是由模型、知识库、工具、工作流、权限和日志共同组成；其中工作流负责流程节点、条件分支、变量处理和人工确认，Agent 负责理解任务和动态调用能力。

## 八、五种工程如何连成一条链路

可以把一个可靠的 Agent 任务分成下面几层：

```text
用户目标
    ↓
提示词工程：明确任务、角色、格式和边界
    ↓
上下文工程：准备文档、历史、工具结果和任务状态
    ↓
驾驭工程：编排能力、限制权限、保存状态、执行验证
    ↓
循环工程：根据观察结果继续行动，直到满足停止条件
    ↓
节点工程：把动作拆成节点，连接顺序、分支和协作关系
    ↓
最终交付：结果可验证、过程可追踪、失败可恢复
```

在实际使用中，可以按照故障表现定位问题：

| 现象 | 更可能的问题层次 | 改进方向 |
|---|---|---|
| 回答模糊、格式错误 | 提示词工程 | 收紧指令，提供模板和示例 |
| 不知道项目背景、遗漏关键资料 | 上下文工程 | 调整检索、过滤和信息组织 |
| 多轮任务逐渐跑偏 | 上下文或状态管理 | 压缩历史，保存外部状态，重新组装上下文 |
| 没测试就宣布完成 | 驾驭工程 | 增加完成标准和自动验证门槛 |
| 反复失败或陷入循环 | 驾驭工程 | 增加重试上限、错误分类和恢复策略 |
| 越改越乱、文档逐渐失效 | 熵管理 | 定期扫描、重构和更新文档 |

## 九、一个可复用的 Agent 任务模板

下面的模板把五种工程的思路放到了一起：

```text
你是一名【角色】。

任务目标：
完成【具体任务】，最终交付【可验收的结果】。

可用上下文：
<project_context>
【项目背景、相关文件、已有约定】
</project_context>

工作规则：
1. 开始修改前，先检查相关文件和现有实现。
2. 将任务拆成可独立验证的步骤。
3. 只修改任务范围内的文件。
4. 不确定时说明缺少的信息，不要猜测。
5. 每完成一个阶段，运行对应的测试或检查。
6. 所有验证通过前，不要宣布任务完成。

输出要求：
1. 先给出执行计划。
2. 完成后列出修改内容。
3. 给出运行过的验证命令和结果。
4. 说明仍然存在的风险或未解决问题。
```

这段模板仍然不是万能的，但它已经从“请 AI 帮我做事”推进到“让 AI 在一个有边界、有反馈、有验收标准的流程里做事”。

长期使用后，可以保存：

- 常用提示词模板；
- 项目上下文入口文件；
- 任务拆解模板；
- 自动化验证脚本；
- 常见失败案例；
- 提示词和工作流的版本记录。

这样积累的就不只是几段好用的提示词，而是一套可重复使用的 AI 工作系统。

## 十、最后的理解

提示词工程、上下文工程、节点工程、驾驭工程和循环工程确实是连在一起的，但它们解决的问题不在同一个层面：

```text
提示词工程：让模型听懂
上下文工程：让模型知道
驾驭工程：让 Agent 做成
```

提示词工程是起点，因为任务必须先被表达清楚；上下文工程决定模型是否拥有完成任务所需的信息；节点工程把复杂任务拆成可组合、可验证的执行单元；驾驭工程为这些单元提供权限、状态和质量护栏；循环工程则让系统能够根据反馈持续推进，直到达到明确的完成条件。

真正成熟的 AI 应用，不是依赖一条越来越长的提示词，而是把这五层结合起来：用清晰指令定义方向，用精准上下文提供依据，用节点组织任务，用驾驭工程设置护栏，再用循环和反馈不断修正过程。

从这个角度看，AI 时代的工程师价值也正在发生变化。过去更多是直接编写每一行代码，未来则会越来越多地设计任务、上下文、工具、约束和反馈系统，构建一个能够帮助人稳定完成工作的“智能生产环境”。
