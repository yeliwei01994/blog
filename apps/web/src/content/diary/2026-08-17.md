### Nginx、服务器、网关的学习

### Nginx

今日学习 Nginx，并且补齐一下服务器、网关等知识。
在进入Nginx的学习之前我觉得应该先了解一下为何需要HTTP服务，想要让本地的浏览器，获取到放在远端服务器上的 html 可以在远端服务器启动一个进程，这个进程对外提供 http 服务，简单来说就是提供了个 url。用户在浏览器中输入这个 url， 回车，浏览器就会向 这个进程发起 http 请求，进程收到浏览器的请求后，就将 html 文件发给浏览器，浏览器完成解析和展示，而像这种根据浏览器请求，返回 html 文件的服务进程，其实就叫 http 服务器。有了它，html 文件就能部署到远端服务器上，对外提供网页服务了。Nginx 就可以充当 HTTP 服务器。
```text
浏览器
  ↓  HTTP 请求：请给我 /index.html
服务器上的 HTTP 服务器进程
  ↓  读取文件
/var/www/index.html
  ↓  HTTP 响应
浏览器
```
像是如果让后端程序直接发这些文件，像是Node、Rust都能返回 HTML、JS 和图片。但如果一个网站有大量静态资源，让业务应用既处理订单、登录、数据库，又处理所有静态文件，更自然的分工应该是：
```
浏览器
  ↓
Nginx
  ├─ 静态文件：Nginx 直接返回
  └─ 动态请求：交给业务后端
```
除此之外正常的网站并不会只有静态的文件，真实网站还需要动态数据。例如用户打开商品页面等，这个请求不能只读一个固定文件，因为商品价格、库存、评价随时会变。此时的业务逻辑：
```
浏览器
  ↓ 请求商品信息
后端程序
  ↓ 查询数据库
数据库
  ↓ 返回商品数据
后端程序
  ↓ 返回 JSON
浏览器
```
此时如果直接让浏览器访问后端，会出现几个问题，一是后端的端口暴露了，用户直接知道了内部机器的IP和端口，此外如果以后你从 8080 改成 3000，或换服务器，前端代码也要改。
还有就是将来如果上线用户量增大，后端的服务器从一台扩容为多台，浏览器该访问哪一台？让浏览器自己随机选后端是糟糕的设计，后端节点变动时，每个客户端都需要更新；健康状态也无法统一判断。
前端与后端端口不同，它们协议、域名、端口都不同，浏览器会受到同源策略限制。

### 反向代理
在外部流量和后端服务之间加一个统一入口，有了反向代理，我们对外就可以只提供一个url域名，背后根据需要, 随时扩缩容服务。
这个反向代理的功能，正好可以加到前面放 html 文件的进程上。那现在这个进程既可以为 前端 html 文件提供 http 服务器的功能，当 html 文件被加载到浏览器，并向后端发起请求的时候，这个进程还能为后端服务器提供反向代理的功能。
```
浏览器
  ↓
https://www.example.com
  ↓
Nginx
  ├─ 请求 /        → 返回前端静态文件
  └─ 请求 /api/*   → 转给后端服务
                      ↓
                 10.0.0.11:8080
```
用户始终只访问一个地址。
接下来就是需要通过配置告知Nginx应该如何转给后端，Nginx 根据请求路径做分流：
```
/             → 前端页面
/assets/app.js → 前端静态文件
/api/users    → 后端接口
/api/orders   → 后端接口
```
```nginx
server {
    listen 80;

    location / {
        root /var/www/site;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:3000;
    }
}
```
像是这段配置简单来说就是监听80端口，如果用户请求以 / 开头：到 /var/www/site 目录找静态文件。但如果用户请求以 /api/ 开头：不要找文件，转发到本机 3000 端口的后端程序，路径决定请求去哪里。
此外负载均衡的能力，也是通过反向代理实现的，像这种，屏蔽掉背后具体有哪些服务器的代理方式，就是我们常说的反向代理。

### 负载均衡
假设在业务场景下，当前的后端服务器只有一台，一开始没有问题，用户变多后，服务 A 的 CPU、内存、数据库连接可能逐渐不够用。你新增两台一模一样的商品，它们处理同一种业务、访问同一套数据库或共享数据。但是就会引出一个问题，用户的请求来了，应该交给A还是B还是C？Nginx负载均衡就是解决这个问题的。
如果没有负载均衡用户直接访问后端A，即使 B、C 很空闲，A 也可能被压垮，更糟糕的是，A 挂掉后，用户会直接失败，浏览器不应该负责发现、选择和切换后端节点。
Nginx 充当统一入口：
```
                        ┌→ 服务 A
浏览器 → Nginx ─────────┼→ 服务 B
                        └→ 服务 C
```
Nginx 决定把本次请求交给谁，这就是负载均衡。
配置例子如下：
```nginx
upstream product_service {
    server 10.0.0.11:8080;
    server 10.0.0.12:8080;
    server 10.0.0.13:8080;
}
# 定义一个后端服务组
server {
    listen 80;
    server_name www.example.com;

    location /api/products/ {
        proxy_pass http://product_service;
    }
    # 当请求命中 /api/products/ 时，转给 product_service 中的一台机器。
}
```
Nginx 在没有额外配置的情况下默认按轮询分发。
```
第 1 个请求 → A
第 2 个请求 → B
第 3 个请求 → C
第 4 个请求 → A
第 5 个请求 → B
```
此外还有一种情况，当各请求耗时差异很大，应当采用最少连接的配置方案。
```nginx
upstream product_service {
    least_conn;

    server 10.0.0.11:8080;
    server 10.0.0.12:8080;
    server 10.0.0.13:8080;
}
```
新请求优先交给当前活跃连接数更少的后端。对请求处理时间差异较大的场景，常比单纯轮询合理。
还可以给每台后端设置失败判定：
```nginx
upstream product_service {
    server 10.0.0.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.0.12:8080 max_fails=3 fail_timeout=10s;
    server 10.0.0.13:8080 max_fails=3 fail_timeout=10s;
}
```
一台后端挂了的话，在 10 秒内，某服务连续失败 3 次，Nginx 就会暂时认为它不可用，一段时间内不再优先把请求发给它。

### 并发
假设有1万人打开了你的网站，不代表Nginx正在同时做1万件CPU计算，很多用户只是在进行打开网站后的阅读，请求发到后端在等待数据查询的结果等，这些都叫连接还存在，但绝大部分时间没有CPU工作要做，所以一万个并发的链接并不等于CPU同时计算一万件事情，Nginx 的强项，就是高效地管理这些大多数时间在等待的连接。
在传统服务器处理流程，处理流程大概是如下：
```
接收请求
→ 转给后端
→ 后端查数据库
→ 等待查询结果
→ 返回结果
```
假设数据库查询耗时 500ms。在 2ms ~ 500ms 之间，它几乎什么都没做，只是在等网络和后端。
```
处理者 1：
0ms    收到 A
1ms    转发给后端
2ms    开始等待后端
500ms  后端返回
501ms  返回给 A
```
这就是一请求占一个线程/进程直到完成的问题。
Nginx解决这个问题的做法就是等待的时候把控制权让出来，Nginx的worker处理A时，不会一直坐着等，worker 没有忘掉 A；它只是把 A 的下一步挂起来，等事件发生再继续。这也叫做异步非阻塞 I/O。
```
0ms     处理 A，发给后端
2ms     A 等待后端；worker 改去处理 B

3ms     处理 B，发给后端
5ms     B 等待后端；worker 改去处理 C

6ms     处理 C，发给后端
8ms     C 等待后端；worker 继续处理新请求

500ms   A 的后端返回
        操作系统通知 worker
        worker 处理 A 的响应并发回浏览器
```
所以对用户而言，很多请求像是同时进行的，这叫并发。但如果机器只有一个 CPU 核，某个瞬间 CPU 仍只能执行一段指令，真正同时使用多个 CPU 核，叫并行。Nginx 同时利用两者。因此常见配置为：
```nginx
worker_processes auto;
```
让 Nginx 大致按 CPU 核数启动 worker。

#### Master 和 Worker

Nginx 不是让多个 Worker 分别绑定同一个端口，实际是 Master 启动时先创建并绑定 `IP:80` 的监听 socket，再创建多个 Worker；Worker 继承并共同使用这个监听 socket。客户端的新连接先进入操作系统维护的等待队列，某个 Worker 调用 `accept()` 时，内核会原子地把这一个连接交给它，其他 Worker 不会再处理同一连接，因此既不会端口冲突，也不会重复接收。Nginx 和操作系统还会协调多个 Worker 接收连接，避免所有 Worker 因一个新连接同时被唤醒。

此外，配置 reload 时，新 Worker 接收新连接，旧 Worker 完成已有连接后退出，保证任意时间一直有 Worker 在工作。也就是所谓的滚动升级。因此还需要一个新的进程协调各个 Worker 谁先谁后，这个协调进程，就是所谓的 Master 进程。
```
worker_processes auto;

server {
    listen 80;
}
```
实际Nginx的工作流程如下：
```
1. master 启动
2. master 创建并绑定监听 socket：0.0.0.0:80
3. master 开始监听这个 socket
4. master 创建 Worker # 数量根据 CPU 核数，也可以自定义
5. worker 继承/共享这个监听 socket
```
#### 共享内存与模块化网关能力

多 Worker 进程的情况下，同一个客户端的多个请求会随机打到某个 Worker。对于限流这种需要计数的场景，计数会被分散到多个 Worker 上单独处理，所以还需要给这些 Worker 进程分配一个共享内存区域，方便多个进程之间共用同一份数据做逻辑，确保系统数据一致性。
此外在它上面也可以加入一些通用网关能力，比如加个日志，记录每次调用的结果，方便后续排查问题，又比如加个对输入输出的内容进行压缩的功能，减小网络带宽消耗，又或者是对某个 IP 进行限流或封禁，甚至还可以修改输入输出的内容。这部分功能设计为开放接口，让用户通过自定义模块来实现特定功能。像是基础网关只支持http，可以通过自定义模块让它支持tcp，udp，http2和websocket，Nginx的生态非常丰富，资料和模块也是非常的多，那么多种能力，可以通过配置文件，也就是nginx.conf，想用什么能力，就在配置文件上声明清楚就行。

#### Proxy Cache

作为网关，它在收到前端网页请求后，会转发给后端，并将后端处理结果中转给前端。如果它能将响应结果缓存起来，下次收到同样的请求时，就可以直接将缓存里的数据返回给前端，从而减少响应时间和网络负载。如果将数据放进内存里，内存较贵，不太合适；可以维护一些磁盘文件，用于在前端请求后端的过程中暂存后端响应的结果。后面再有相同请求，就可以将磁盘里的数据返回。这又是经典的空间换时间，用廉价的磁盘空间换取网络传输和 CPU 计算耗时。对于后端响应较慢或重复请求较多的场景，读写磁盘通常比直接将请求打到后端来得快。这些用于缓存响应数据的磁盘文件，就是所谓的 Proxy Cache。

### chatbot 项目
在这项目中的 Caddy 只承担 HTTP 反向代理和基于 Host/路径的路由，Nginx 能完整覆盖，进行项目的优化，Nginx的生态更加成熟稳定，方便后续的迭代更新。
```nginx
events {}

http {
    map $http_upgrade $connection_upgrade {
        default upgrade;
        ""      close;
    }

    server {
        listen 80;
        server_name example.localhost;

        location ^~ /api/ {
            proxy_pass http://127.0.0.1:4173;
            proxy_http_version 1.1;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
            proxy_set_header Upgrade $http_upgrade;
            proxy_set_header Connection $connection_upgrade;
        }

        location = /healthz {
            proxy_pass http://127.0.0.1:4173;
            proxy_http_version 1.1;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
            proxy_set_header Upgrade $http_upgrade;
            proxy_set_header Connection $connection_upgrade;
        }

        location / {
            proxy_pass http://127.0.0.1:3000;
            proxy_http_version 1.1;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
            proxy_set_header Upgrade $http_upgrade;
            proxy_set_header Connection $connection_upgrade;
        }
    }

    server {
        listen 80;
        server_name ~^(?<project>.+)\.example\.localhost$;

        location / {
            proxy_pass http://127.0.0.1:4173;
            proxy_http_version 1.1;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
            proxy_set_header Upgrade $http_upgrade;
            proxy_set_header Connection $connection_upgrade;
        }
    }
}
```
让 Nginx 作为项目唯一的访问入口。浏览器访问 example.localhost 时，Nginx 会先判断请求内容：如果是 /api/ 开头的接口请求，或者 /healthz 健康检查，就转发给 Rust 后端的 4173 端口；如果是打开工作台页面、加载前端资源等其他请求，就转发给 Next.js 的 3000 端口。访问 coffee-demo.example.localhost 这类项目子域名时，Nginx 会统一交给 Rust 后端处理，因为后端需要根据访问的域名判断应该返回哪个已发布项目。配置里的 proxy_set_header 是把用户原本访问的域名、客户端 IP 和访问协议传给后端，其中最重要的是 Host，没有它，后端就无法区分不同项目子域名。
