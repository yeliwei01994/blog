### 本周学习主题

本周围绕 Nginx、MySQL、Redis 和 Docker 四项技术展开学习，同时补充 Markdown 文档写作与代码展示规范。学习重点不只是记住命令和概念，而是理解每项技术解决什么问题、应该保存什么数据、如何与其他服务配合，以及出现故障时应该从哪里排查。

## 一、本周的学习收获

这周学习下来，我对四项技术的分工有了更具体的认识。Nginx 主要解决请求入口、静态资源和反向代理的问题；MySQL 负责保存需要长期查询的数据，并通过索引、事务和日志保证数据能够被正确使用；Redis 更适合缓存、队列和变化较快的临时状态；Docker 则负责把不同服务的运行环境、网络和启动方式统一起来。

以前看这些内容时，我容易把注意力放在命令和配置上。这次边学边整理后，开始能把命令和实际问题联系起来：为什么请求需要反向代理，为什么耗时任务要放到队列里，为什么缓存不能代替数据库，以及为什么容器重启后还需要单独考虑数据保存。

另外，本周也补充了 Markdown 的写作方式。技术内容如果只是连续堆在一起，后面很难复习和查找；使用合适的标题、代码块、表格和流程图，可以让学习过程和代码示例更容易被别人理解，同时主要是方便自己回看。



## 二、技术一：Nginx

### 1. 从 HTTP 服务理解 Nginx

浏览器输入 URL 后，需要有一个对外提供 HTTP 服务的进程接收请求，再返回 HTML、JavaScript、图片或 JSON。Nginx 可以作为 HTTP 服务器直接返回静态文件，也可以作为反向代理把动态请求转给后端应用。

```text
浏览器
    │  GET /index.html
    ▼
Nginx
    ├── 静态文件：直接读取 /var/www/index.html
    └── 动态请求：转发给 Rust API
```

如果所有请求都由业务应用处理，后端就需要同时负责业务逻辑、数据库访问和大量静态资源。将静态文件和动态请求分开，可以让业务服务更专注于登录、任务和数据处理。

### 2. 反向代理示例解析

```nginx
server {
    listen 80;
    server_name example.com;

    location / {
        root /usr/share/nginx/html;
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://api:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

这段配置可以这样理解：

1. `listen 80` 让 Nginx 监听 HTTP 端口。
2. `location /` 处理普通页面请求，从静态目录读取前端资源；`try_files` 适合单页应用的前端路由回退。
3. `location /api/` 匹配 API 请求，并将请求转发到 Docker 网络中的 `api:8080`。
4. `proxy_set_header` 把原始主机和客户端地址传给后端，便于日志、审计和问题排查。

前端只需要请求 `/api/v1/videos/upload`，不需要知道 Rust API 的内部端口。以后 API 换机器、换端口或增加副本时，浏览器端的请求路径仍然可以保持稳定。

### 3. 负载均衡与并发模型

Nginx 还可以将请求分配给多个后端实例：

```nginx
upstream api_servers {
    server api-1:8080;
    server api-2:8080;
}

server {
    listen 80;

    location /api/ {
        proxy_pass http://api_servers;
    }
}
```

这里的 `upstream` 定义了后端服务组，Nginx 默认可以使用轮询方式分发请求。

本周还了解了 Nginx 的 Master/Worker 模型：Master 负责读取配置、管理 Worker 和处理重载；Worker 负责实际接收和处理连接。这样可以在不中断已有连接的情况下完成配置更新，也能通过多个 Worker 处理并发请求。


## 三、技术二：MySQL

### 1. 从数据页到索引

本周对 MySQL 的理解从“保存几张表”进一步深入到存储引擎如何组织数据。InnoDB 会以数据页为基本单位读写数据，Buffer Pool 用来缓存热点页，索引则帮助数据库减少无效扫描。

MySQL 常用 B+ 树索引，主要原因是它的非叶子节点只保存键和指针，能够在一个节点中放入更多索引项；叶子节点按顺序连接，既适合等值查询，也适合范围查询和排序。

```sql
CREATE TABLE video_jobs (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    filename VARCHAR(255) NOT NULL,
    status VARCHAR(32) NOT NULL,
    created_at DATETIME NOT NULL,
    INDEX idx_status_created (status, created_at)
);

SELECT id, filename, status
FROM video_jobs
WHERE status = 'processing'
ORDER BY created_at DESC
LIMIT 20;
```

`idx_status_created` 是联合索引。查询先按 `status` 筛选，再按 `created_at` 排序，能够减少扫描范围。索引不是越多越好，因为写入时需要同步维护索引，并且索引也会占用内存和磁盘空间。

### 2. 事务与日志的分工

本周重点理解了 Undo Log、Redo Log 和 Binlog 的区别：

- **Undo Log**：保存修改前的信息，用于回滚事务和支持 MVCC。
- **Redo Log**：记录数据页的物理修改，保证数据库崩溃恢复时能够重做已经提交的操作。
- **Binlog**：记录逻辑层面的变更事件，常用于主从复制和增量恢复。

例如创建任务时，任务记录和任务状态不应出现明显不一致，可以使用事务：

```sql
START TRANSACTION;

INSERT INTO video_jobs (filename, status, created_at)
VALUES ('demo.mp4', 'pending', NOW());

INSERT INTO job_events (job_id, event_type, status)
VALUES (LAST_INSERT_ID(), 'job_created', 'recorded');

COMMIT;
```

如果中间步骤失败，应执行 `ROLLBACK`，而不是让前端自行猜测数据库到底完成了哪一步。实际项目中还需要根据表结构、隔离级别和并发场景继续验证事务边界。

### 3. 事务如何避免库存超卖：一个通用例子

```sql
START TRANSACTION;

SELECT stock
FROM products
WHERE id = 1
FOR UPDATE;

UPDATE products
SET stock = stock - 1
WHERE id = 1 AND stock > 0;

COMMIT;
```

`FOR UPDATE` 会锁定需要修改的行，让并发事务按顺序处理；`stock > 0` 又是最后一道业务条件检查。视频任务虽然不是库存场景，但相同的思路适用于“同一个任务只能被一个 Worker 抢到”或“同一个事件不能重复确认”等问题。

## 四、技术三：Redis

### 1. 数据结构与使用场景

本周学习了 Redis 常见数据结构，并将它们与项目场景对应起来：

| 数据结构 | 常用场景 | 视频平台中的可能用途 |
| --- | --- | --- |
| String | 简单值、计数器、过期缓存 | 任务进度、限流计数、去重标记 |
| Hash | 一组字段 | 保存任务的临时状态 |
| List | 简单队列 | 轻量级任务等待队列 |
| Set | 去重和集合运算 | 用户权限、已处理任务集合 |
| Sorted Set | 带分值排序 | 延迟任务、按优先级处理 |
| Stream | 可追踪的消息流 | 视频处理任务和消费记录 |

简单的缓存示例：

```text
SET video:job:job_001:progress "45" EX 3600
GET video:job:job_001:progress
```

`EX 3600` 表示让进度在一小时后自动过期，避免临时数据无限占用内存。但过期只是清理机制，不代表任务最终结果已经保存；最终状态仍应写回 MySQL。

### 2. 为什么视频处理需要异步队列

视频上传后通常还要抽帧、检测、跟踪、规则判断，甚至调用大模型。如果 API 一直等待完整处理结束，用户会长时间占用一个 HTTP 请求，超时后也很难判断任务是否已经执行了一部分。

更合理的流程是：

```text
API 创建任务
    ↓
Redis Stream / 队列
    ↓
Worker 消费任务
    ↓
更新处理进度
    ↓
MySQL 保存最终状态和事件
```

任务消息需要包含足够的信息，而不是只有一句“处理这个视频”：

```json
{
  "job_id": "job_001",
  "source_uri": "/media/videos/demo.mp4",
  "detector_version": "mock-v1",
  "rule_version": "rule-v1",
  "created_at": "2026-08-23T10:20:00Z"
}
```

Worker 取到消息后，先根据 `job_id` 查询 MySQL，确认任务没有完成或取消，再将状态改为 `processing`。成功后写入事件并改为 `completed`；失败后记录错误原因，再根据重试次数决定是否重新投递。

### 3. Redis 可靠性边界

本周也认识到，“使用队列”不等于“任务一定可靠”。后续需要继续考虑：

- 消费者组和消息确认，避免消息被取走后直接丢失。
- Worker 中途退出时，任务能否重新被领取。
- 失败重试是否有上限，反复失败的任务是否进入死信队列。
- 同一个任务重复消费时，是否具备幂等性。
- 用户取消任务后，Worker 是否会检查取消状态。
- Redis 暂时不可用时，API 应该返回什么错误，是否允许稍后重试。

例如，任务开始处理前可以用数据库条件更新控制抢占：

```sql
UPDATE video_jobs
SET status = 'processing', started_at = NOW()
WHERE id = ? AND status = 'queued';
```

只有更新成功的 Worker 才能继续处理任务。这样即使消息重复投递，也不会让两个 Worker 同时执行同一个处于 `queued` 状态的任务。

### 4. 缓存问题的基本认识

缓存击穿、缓存雪崩和缓存穿透都可能影响系统稳定性：

- **缓存击穿**：某个热点键突然失效，大量请求同时访问数据库。
- **缓存雪崩**：大量键在相近时间过期，数据库瞬间承受高压力。
- **缓存穿透**：查询大量不存在的数据，缓存和数据库都被反复访问。

对应的常见处理方式包括热点数据加互斥锁、过期时间增加随机值、对空结果短暂缓存，以及对输入参数做校验。当前视频平台主要使用 Redis 做异步任务和临时进度，缓存策略需要等真实查询场景稳定后再细化。

## 五、技术四：Docker

### 1. 镜像、容器和 Dockerfile

Docker 的价值不只是“把程序打包后部署”，更重要的是将代码、运行时、依赖和启动方式描述清楚，使开发、测试和部署环境更接近。

可以把镜像理解为模板，把容器理解为镜像启动后的运行实例：同一个镜像可以创建多个容器，每个容器有自己的进程、网络和文件系统视图。

```dockerfile
FROM rust:1.85 AS builder
WORKDIR /app
COPY backend/ .
RUN cargo build --release

FROM debian:bookworm-slim
WORKDIR /app
COPY --from=builder /app/target/release/backend /app/backend
EXPOSE 8080
CMD ["/app/backend"]
```

这是一个多阶段构建示例。第一阶段负责编译，第二阶段只复制最终可执行文件，不把 Rust 编译器和完整源码带入运行镜像，可以减小镜像体积并降低运行环境复杂度。

### 2. Compose 如何组织多服务

```yaml
services:
  api:
    build: ./apps/api
    environment:
      DATABASE_URL: mysql://app:password@mysql:3306/video
      REDIS_URL: redis://redis:6379
    depends_on:
      mysql:
        condition: service_healthy
      redis:
        condition: service_started

  mysql:
    image: mysql:8.4
    environment:
      MYSQL_DATABASE: video
      MYSQL_USER: app
      MYSQL_PASSWORD: password
      MYSQL_ROOT_PASSWORD: root-password
    volumes:
      - mysql_data:/var/lib/mysql

  redis:
    image: redis:7

volumes:
  mysql_data:
```

这里的关键点是：容器之间使用服务名连接，例如 API 连接 `mysql:3306` 和 `redis:6379`，而不是依赖宿主机的 `localhost`。`mysql_data` 是数据卷，容器重新创建后，数据库数据仍可以保留。

实际项目中还应把密码放到 `.env` 或密钥管理系统，并将 `.env` 加入 `.gitignore`；`.dockerignore` 则应排除 `.git`、`node_modules`、构建产物和敏感配置，避免把不必要或不应公开的内容打进镜像。

### 3. Docker 网络与数据持久化

视频平台的服务关系可以简化为：

```text
nginx
  ├── frontend
  └── api ─── mysql
          └── redis

worker ─── mysql
        └── redis
```

浏览器只访问 Nginx 对外暴露的端口；Nginx 通过 Compose 网络访问 API；API 和 Worker 通过内部网络访问 MySQL、Redis。MySQL 和 Redis 不必全部暴露到公网，这样可以减少外部攻击面。

还需要区分两种数据：

- MySQL 任务和事件数据需要数据卷或独立数据库保证持久化。
- 视频、截图和短片段不适合直接放入数据库，应该使用文件目录、对象存储或独立媒体存储，并在 MySQL 中保存地址和元数据。

### 4. Compose 的验证顺序

容器显示 `Up` 只能说明进程暂时启动，不能证明业务完整可用。本周形成的排查顺序是：

1. 检查容器是否启动。
2. 检查 MySQL、Redis 健康状态。
3. 检查 Nginx 是否能访问 API。
4. 检查 API 是否能写入 MySQL 和 Redis。
5. 检查 Worker 是否真的消费到任务。
6. 检查任务状态、事件结果和前端页面是否一致。

这个顺序可以把“端口问题、网络问题、数据库问题、队列问题和业务问题”分开，减少只盯着前端页面排查的情况。

### 3. 代码示例的写法

技术文档中的代码不能只贴出来，还需要说明它解决什么问题、关键字段是什么、运行后会产生什么结果。例如 Docker Compose 代码中，应该解释服务名、环境变量、依赖关系和数据卷，而不是只给出一段 YAML。

```sql
SELECT id, status
FROM video_jobs
WHERE status = 'processing'
ORDER BY created_at DESC
LIMIT 20;
```

这条 SQL 的说明应该至少包含：查询目标是任务表，筛选条件是处理中任务，结果按创建时间倒序排列，最多返回 20 条。这样读者能够理解代码和业务含义之间的关系，也方便后续检查索引是否匹配查询条件。

### 4. 技术文档的阅读友好性

后续写日报和周报时需要注意以下几点：

- 一个标题只表达一个主题，避免在同一小节中混合多个无关概念。
- 先写结论和作用，再写原理和细节，降低阅读门槛。
- 代码块前说明使用场景，代码块后解释关键行。
- 流程图只保留关键节点，避免把所有实现细节堆在一张图里。
- 表格用于对比和归纳，不用于替代大段解释。
- 链接和参考资料集中放在文章末尾，正文只保留必要的引用。
- 技术名词、状态值、命令和文件名使用反引号，避免和普通文字混淆。
